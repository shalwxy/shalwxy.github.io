## 문제

운영 에러는 Slack 채널에 올라온다. 담당자는 에러를 보면 늘 같은 세 가지를 한다.

1. 스택트레이스에서 **어느 파일·어느 코드**인지 찾는다
2. **전에도 본 에러인지** 채널을 검색한다
3. 최근 배포 중 **무엇이 바뀌어서** 났을지 커밋 로그를 뒤진다

세 가지 다 기계적인 일인데도 사람이 직접 한다. 그래서 밤이나 주말에는 처리가 느려진다. 이 셋을 봇이 먼저 해 두고 사람은 판단만 하게 만드는 것이 목표였다.

"에러 텍스트를 LLM에 던지면 되지 않나"가 첫 생각이었고, 1단계는 실제로 그렇게 시작했다. 그 뒤로 추가한 것들이 이 글의 본론이다 — **LLM을 그냥 던지는 도구로 쓰지 않기 위한 장치들.**

## 1단계 — 에러 텍스트만 분석

### 접근

Slack 이벤트로 에러 메시지를 받아 LLM에 "이 에러의 원인과 조치를 설명해 줘"로 보내고, 답을 스레드에 단다.

### 결과

**부분 성공** — 답은 그럴듯했지만 **일반론**이었다. "nil pointer dereference는 초기화되지 않은 포인터를 참조할 때…" 같은 교과서 설명. 담당자가 원하는 "**우리 코드의 어디**"와 "**이번 배포에서 뭐가 바뀌었나**"가 없다.

### 분석

LLM이 모르는 것은 **우리 저장소**다. 에러 텍스트만으로는 코드 맥락이 없어 일반론밖에 못 한다. 답의 질을 올리려면 LLM을 바꾸는 게 아니라 **프롬프트에 우리 맥락을 넣어야** 한다.

## 2단계 — 소스와 최근 커밋을 프롬프트에 주입 (채택)

### 접근

스택트레이스에서 **파일 경로를 추출**하고, 각 파일에 대해 **GitLab API로 최근 커밋 5개**를 조회해 "회귀 후보"로 프롬프트에 넣는다. 해당 줄 주변의 소스도 함께.

```
[에러]
panic: runtime error: invalid memory address
  at internal/order/service.go:463
  at internal/order/handler.go:58

[service.go:450-480 소스]
...

[service.go 최근 커밋]
- 2일 전  a1b2c3  fix: 분기 추가
- 9일 전  d4e5f6  refactor: validator 완화
...

위 정보로 원인 후보와 조치를 답하라. 참고 자료에 없는 코드명은 인용하지 말 것.
```

### 결과

**성공** — 답이 "**2일 전 커밋 a1b2c3에서 추가된 분기에서 `req.ToAddress`가 nil일 때 역참조**" 수준으로 구체화됐다. 담당자는 커밋 하나를 열어 확인하면 된다.

### 분석

LLM의 값은 **추론**이지 **지식**이 아니다. 지식(우리 코드, 최근 변경)은 우리가 넣어 주고, LLM은 그 안에서 추론하게 한다. "회귀 후보 = 최근 커밋"은 사람이 하던 3번 작업을 그대로 자동화한 것이다. 이 자동화가 답의 질을 가장 크게 올렸다.

## 운영하면서 붙인 가드레일

2단계가 live에 켜지고 나서, 실제 사용에서 드러난 문제마다 장치를 하나씩 더했다. "LLM 호출" 바깥의 **서비스 로직**이다.

### 분석 재사용 — 같은 에러는 한 번만

같은 에러가 하루에 수십 번 올라온다. 매번 LLM을 부르면 비용도 들고, 담당자 입장에선 **같은 분석이 수십 개 스레드에 달린다.**

- 스택트레이스를 정규화해 **signature**(파일·줄·에러 종류의 해시)를 만든다
- 분석 결과를 OpenSearch에 signature 키로 저장하고, **90일 안에 같은 signature**가 오면 저장된 분석을 재사용한다
- 응답 footer에 **최초 감지 시각**과 **원본 스레드 링크**를 붙여 "이거 전에도 났었다"를 바로 보여 준다

### escalation — 반복은 경고 한 번으로

같은 에러가 **5분 안에 10회** 넘게 오면, 매번 분석을 달지 않고 **경고 메시지 하나**만 올린다. 폭주 중에 스레드마다 분석이 붙으면 채널이 읽을 수 없게 된다.

### 동시성·비용 상한

- LLM 분석의 **동시 실행 수를 세마포어로 제한**(기본 2). 에러가 폭주해도 LLM 호출이 그만큼 폭주하지 않는다.
- **일·월 비용 상한.** 넘으면 분석을 멈추고 "예산 초과" 안내만 단다.
- 벤더 429/5xx는 **Retry-After 헤더 우선**, 없으면 **지수 백오프 + 지터**로 최대 3회 재시도.
- GitLab 조회에 **서킷 브레이커.** GitLab이 느려지면 소스 주입을 생략하고 에러 텍스트만으로 분석한다(1단계로 degrade).

### 자기 격리 — 대역별 pod는 자기 대역만

dev·stage·live 알림 채널이 따로 있고, 봇 pod도 대역별로 뜬다. 각 pod가 **자기 대역 채널만** 처리하게 해, live 봇이 dev 에러로 바쁘거나 dev 봇이 live 분석을 다는 일을 막는다.

### PII·토큰 마스킹

LLM에 보내기 전에 이메일·지갑 주소·토큰 문자열 패턴을 마스킹한다. 에러 메시지에는 사용자 식별자가 섞여 들어오기 쉽다.

## 프롬프트 규율 — 실패 모드를 규칙으로

답이 **그럴듯하지만 틀린** 경우를 모아 프롬프트의 규칙으로 승격했다.

| 실패 모드 | 규칙 |
|---|---|
| 외부 서비스 타임아웃인데 "pod를 재시작하세요"부터 권함 | **원인 소유권을 먼저 판별**하라. 외부 원인이면 우리 쪽 조치를 권하지 말 것 |
| 임시 우회책을 근본 해결처럼 서술 | 조치마다 `[근본 해결]` / `[임시 우회]` 라벨 필수 |
| 참고 자료에 없는 함수·파일 이름을 지어냄 | 참고 자료에 없는 코드명은 인용 금지 |

세 번째 규칙이 가장 효과가 컸다. 환각의 상당수는 "있을 법한 이름"을 만들어 내는 것이었다. "자료에 없으면 말하지 말라"는 규칙을 넣은 뒤로 대부분 사라졌다.

### 잘린 메시지 사건

한 번은 봇이 사내 패키지 이름을 **`io.netty`로 오추정**했다. 원인은 Slack 이벤트로 받은 본문이 **루트 메시지의 미리보기만 잘려** 온 것 — 스택트레이스 윗부분만 보고 추론한 결과였다. 이후 **잘림 판별**(`LooksTruncated`) → 스레드 replies 재조회 → RichText 블록에서 전문 추출 순서를 넣었다. LLM의 추론은 입력이 온전할 때만 의미가 있고, **입력이 잘렸는지는 LLM이 알 수 없다.**

## 인터랙션 — 리액션 하나로

답에 대한 피드백·재분석·상태 표시를 전부 **이모지 리액션**으로 했다.

- `+1` / `-1` — 분석이 맞았는지 피드백 (저장된 분석의 신뢰도에 반영)
- `🔍` — 재분석 트리거 (수정 배포 뒤 다시 보고 싶을 때)
- 봇이 분석 중이면 `⏳`, 끝나면 `✅`를 봇이 스스로 단다

별도 명령어·버튼 없이, 담당자가 이미 Slack에서 하는 동작 안에서 끝난다.

## 벤더 모델 폐기 — 가장 뻔한 장애

운영 두 달 뒤 **LLM 벤더가 모델 하나를 폐기**해 404가 났다. 봇을 포함한 LLM 기능 전체가 멈췄다. 모델 이름을 설정으로 빼 두어 교체 자체는 금방 했지만, **모델 폐기 공지를 모니터링하지 않았다**는 게 교훈이었다. 이후 404를 "모델 없음"으로 구분해 안내하고, 모델 이름을 환경별 설정으로 관리한다.

## 정리

| 단계 | LLM에 주는 것 | 답의 질 |
|---|---|---|
| 1. 에러 텍스트만 | 에러 메시지 | 일반론 |
| **2. 소스·최근 커밋 주입 (채택)** | 에러 + 해당 파일 소스 + 최근 커밋 5개 | 커밋 단위로 구체적 |

**채택 — 맥락 주입 + 가드레일.** LLM의 몫은 추론이고 지식은 우리가 넣는다. 그리고 LLM 호출 **바깥**에 재사용·상한·격리·마스킹을 두어야 운영에서 버틴다.

- 답이 일반론이면 LLM을 바꾸기 전에 **프롬프트에 우리 맥락**(소스, 최근 변경, 과거 분석)이 있는지 본다.
- 같은 입력은 **한 번만 분석**하고 재사용한다. signature 키 + 보존 기간이면 충분하다.
- **동시성·비용·외부 의존**에 각각 상한을 둔다. 에러 폭주는 곧 LLM 호출 폭주다.
- 환각은 **"자료에 없으면 말하지 말라"**로 가장 많이 줄었다. 실패 모드를 발견하면 규칙으로 승격한다.
- **입력이 온전한지**는 LLM이 판단하지 못한다. 잘림·누락은 봇이 먼저 확인한다.
- 벤더 모델은 **폐기된다.** 모델 이름은 설정으로, 폐기 공지는 모니터링 대상으로.
