## 문제

정책 전용 서비스를 새로 만들 때의 일이다([정책 전용 서비스 글](/lab/engineering/distributed/dedicated-policy-service/)). 이전에 신설된 서비스들을 보면 공통된 모양이 있었다 — **코드는 다 있는데 dev 환경에서만 돈다.** test·qa·stage·live로 올리려면 그때 가서 매니페스트를 복사하고, 게이트웨이 route를 추가하고, CI job을 붙이고, 환경별 시크릿을 넣는다. 이 "뒤로 미룬 일"이 보통 **몇 주 뒤 다른 사람** 몫이 되고, 그 사람은 서비스 코드의 맥락이 없다.

배포 환경은 다섯 단계(dev·test·qa·stage·live)이고, 배포 경로는 크게 셋으로 갈린다.

| 환경 | 배포 경로 |
|---|---|
| dev | CI가 K8s API로 바로 재시작 |
| test · qa · stage | CI가 배포 도구의 job을 호출 |
| live | CI는 이미지 빌드까지만. 배포는 CI 밖에서 사람이 배포 도구로 |

환경마다 경로가 달라서 "dev에서 되니까 나머지도 되겠지"가 성립하지 않는다. 각 환경의 설정이 **실제로 존재하고 한 번은 돌아 봐야** 된다.

## 시도 1 — 코드 먼저, 배포는 나중에

### 접근

서비스 코드와 단위 테스트를 완성하고 dev에 올려 동작을 확인한 뒤, 상위 환경 배포 설정은 "기능이 안정되면" 추가한다.

### 결과

**실패** — 두 가지가 반복됐다.

- **"안정되면"이 오지 않는다.** 기능 요구가 계속 들어오고, 배포 설정 추가는 늘 다음 스프린트로 밀린다. dev에서만 도는 상태가 몇 달 가기도 한다.
- **나중에 추가한 설정은 코드와 어긋난다.** 환경 변수 이름, 포트, 헬스체크 경로가 그 사이 바뀌어 있고, 뒤늦게 매니페스트를 쓰는 사람은 코드를 다시 읽어야 한다. 다른 서비스 매니페스트를 복사해 오면 **그 서비스의 설정이 섞여 들어온다**(불필요한 볼륨, 다른 HPA 임계치).

### 분석

배포 설정은 코드의 **부록이 아니라 코드의 일부**다. 환경 변수·포트·헬스체크·리소스 요구량은 코드가 결정하고, 매니페스트는 그걸 적는 것뿐이다. **코드를 쓴 사람이 코드를 쓰는 그 주에** 적는 것이 가장 정확하고 싸다. 몇 주 뒤의 다른 사람은 같은 정보를 코드에서 다시 캐내야 한다.

## 시도 2 — 코드와 배포 세트를 같은 주에 (채택)

### 접근

서비스 신설 작업의 **완료 조건에 배포 세트를 포함**했다. 세트는 다음 다섯 가지다.

| # | 항목 | 어디에 | 내용 |
|---|---|---|---|
| 1 | Helm 템플릿 | 배포 차트 저장소 | 환경 공통 Deployment·Service·ConfigMap 템플릿 (값은 환경별 주입) |
| 2 | 환경별 매니페스트 | 배포 매니페스트 저장소 | dev · test · qa · stage · live 각각의 Deployment · HPA · Service |
| 3 | 게이트웨이 route | 게이트웨이 설정 저장소 | gRPC → REST 변환 규칙, 인증 적용/skip 목록 |
| 4 | CI 배포 job | 서비스 저장소의 CI 설정 파일 | 이미지 빌드 + 환경별 배포 트리거 (live는 빌드까지만) |
| 5 | 시크릿·설정 | 시크릿 저장소 | DB 접속, 외부 키 — 환경마다 |

```yaml
# CI 설정 파일 (요지)
stages: [build, deploy]

build:
  stage: build
  script: docker build -t $IMAGE:$CI_COMMIT_SHA . && docker push $IMAGE:$CI_COMMIT_SHA

deploy-dev:
  stage: deploy
  script: kubectl -n dev set image deploy/$SVC $SVC=$IMAGE:$CI_COMMIT_SHA
  only: [develop]

deploy-stage:
  stage: deploy
  script: deploy-tool run --job deploy-$SVC --env stage --tag $CI_COMMIT_SHA
  only: [release/*]
  when: manual

# live: 빌드 job만 있고 배포 job은 없음 — CI 밖에서 사람이 실행
```

### 결과

**성공** — 서비스가 만들어진 그 주에 **다섯 환경 모두에 올릴 수 있는 상태**가 됐다. 상위 환경 설정이 코드와 같은 시점에 갖춰져, live 전환은 "설정이 있는지"가 아니라 "기능이 준비됐는지"만 보고 결정했다.

### 분석 — 세트의 가치는 "빠진 게 없다"에 있다

다섯 항목 중 하나라도 빠지면 그 환경에는 올라가지 않는다. 세트를 **체크리스트로 고정**하면 "매니페스트는 했는데 route를 깜빡"이 사라진다. 특히 자주 빠지는 것:

- **게이트웨이 route** — 서비스는 떠 있는데 외부에서 닿지 않는다. "배포는 됐는데 404"의 단골 원인.
- **live 매니페스트** — dev·stage까지는 CI가 알아서 올리니 잘 되는데, live는 사람이 하는 단계라 설정이 없어도 CI는 아무 말도 안 한다.
- **HPA** — Deployment만 복사하고 HPA를 빠뜨리면 live에서 pod 하나로 버티다 터진다.

또 하나, 세트를 **같은 사람이 같은 주에** 만들면 다른 서비스의 매니페스트를 "복사해서 수정"하는 대신 **자기 서비스에 맞게 처음부터** 쓰게 된다. 복사본에 딸려 오는 남의 설정이 없다.

### 세트에 넣지 않은 것

- **모니터링 대시보드·알림 규칙** — 메트릭 이름이 운영 초반에 바뀌어 처음부터 만들면 두 번 일한다. live 전환 직전에 추가.
- **런북** — 장애가 한 번은 나 봐야 쓸 내용이 생긴다.

이 둘은 "코드가 결정하는 것"이 아니라 "운영이 결정하는 것"이라 세트에서 뺐다. 세트의 기준은 **"코드를 쓴 사람이 그 시점에 가장 잘 아는 정보인가"**다.

## 다른 방법 — 서비스 템플릿(scaffold)

세트를 매번 손으로 쓰는 대신, **서비스 생성 스크립트**가 다섯 항목을 한 번에 만들어 주는 방식이다 (Backstage의 software template, cookiecutter 등).

- 얻는 것: 신설 비용이 더 줄고, 조직 표준(라벨·리소스 기본값·헬스체크 경로)이 자동으로 적용된다.
- 치르는 것: 템플릿 자체를 유지보수해야 한다. 환경이 바뀌면 템플릿도 같이 바꿔야 하고, 템플릿이 낡으면 그 낡은 설정이 모든 새 서비스에 퍼진다.
- 서비스 신설이 **분기에 여러 번** 있는 조직이면 템플릿이 맞다. 1년에 한두 번이면 체크리스트로 충분하다.

## 정리

| 방식 | 상위 환경 도달 | 설정 정확성 | 적합한 자리 |
|---|---|---|---|
| 코드 먼저, 배포 나중 | 몇 주~몇 달 | 낮음 (코드와 어긋남) | — |
| **코드와 배포 세트를 같은 주에 (채택)** | 같은 주 | 높음 | 신설이 가끔 있는 팀 |
| 다른 방법. scaffold | 즉시 | 템플릿 품질에 의존 | 신설이 잦은 조직 |

**채택: 시도 2.** 배포 설정은 코드가 결정하는 정보를 적는 것이라, **코드를 쓴 사람이 그 시점에** 쓰는 게 가장 정확하다. 세트를 체크리스트로 고정하면 "하나 빠져서 안 올라가는" 일이 사라진다.

- 서비스 신설의 **완료 조건**에 배포 세트를 넣는다. "dev에서 돈다"는 완료가 아니다.
- 세트는 **빠지면 그 환경에 못 올라가는 것**으로 구성한다 — 매니페스트·route·CI job·시크릿. 모니터링·런북은 운영 시점에.
- live가 수동 배포인 환경에서는 **live 설정이 없어도 CI가 경고하지 않는다.** 체크리스트가 그 공백을 메운다.
- 남의 매니페스트를 복사하면 남의 설정이 따라온다. **자기 서비스 기준으로** 처음부터 쓴다.
