## 문제

N일 동안 매일 모은 저축액(천 원 단위) 기록이 있다. 이 기록에서 **연속된 며칠** 동안 모은 금액의 합이 정확히 M(천 원)이 되는 경우가 몇 번인지 구한다.

- 1 ≤ N ≤ 100,000, 1 ≤ M ≤ 100,000,000
- 각 날의 저축액은 1,000 이하의 자연수(1 이상 — 0이나 음수는 없다)
- 입력: 첫째 줄에 N과 M. 둘째 줄에 N개의 저축액
- 출력: 합이 M이 되는 연속 구간의 개수

```
입력                       출력
8 9                        3
2 1 4 2 1 1 3 2
```

1일~4일(2, 1, 4, 2)의 합은 9다. 2일~6일(1, 4, 2, 1, 1)의 합도 9, 4일~8일(2, 1, 1, 3, 2)의 합도 9다. 이 세 구간이 전부라 답은 3.

> 출처: 인프런 [자바(Java) 알고리즘 문제풀이 입문: 코딩테스트 대비](https://www.inflearn.com/course/자바-알고리즘-문제풀이-코테대비)의 [1131번 문제](https://oj.inflearn.com/problem/1131)를 소재와 예제만 바꿔 재구성했다.

## 공통 코드

아래 시도들은 입력을 읽고 결과를 출력하는 부분을 공유한다. 각 시도에서는 합이 M인 구간의 개수를 세는 `countSubarrays` 메서드만 다르다.

```java
import java.util.Scanner;

public class Main {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        int n = sc.nextInt();
        int m = sc.nextInt();
        int[] arr = new int[n];
        for (int i = 0; i < n; i++) arr[i] = sc.nextInt();

        System.out.println(countSubarrays(m, arr)); // 로직은 각 시도 참고
    }
}
```

## 시도 1 — 시작점마다 더하다가 M 이상이면 멈춤

### 접근

시작 인덱스 `i`마다 뒤로 더해가며 합을 키우다가, 합이 M 이상이 되면 멈춘다. 원소가 모두 양수라 더할수록 합은 커지기만 하므로, 한 번 M을 넘기면 더 더해도 다시 M으로 돌아올 수 없다 — 그래서 멈춘 시점의 합이 정확히 M인지만 보면 된다.

```java
public static int countSubarrays(int m, int[] arr) {
    int cnt = 0;
    for (int i = 0; i < arr.length; i++) {
        int sum = 0;
        for (int j = i; j < arr.length && sum < m; j++) {
            sum += arr[j];
        }
        if (sum == m) cnt++;
    }
    return cnt;
}
```

### 결과

**성공** — 예제에서 `3` 출력.

복잡도: 시간 O(N²)(최악), 공간 O(1). 원소가 1처럼 작고 M이 커서 안쪽 루프가 거의 끝까지 더해야 하는 경우, 시작점 N개마다 거의 N번씩 더하게 된다.

N이 최대 100,000이라 O(N²)이면 최악 100억 번에 이른다. 1,000ms 제한 안에 끝난다고 보장할 수 없다 — 예제처럼 작은 입력에서는 드러나지 않는다.

### 분석

`i`를 하나 옮길 때, 안쪽 `j` 루프는 바로 앞 시작점이 이미 더해 둔 값들을 전혀 재사용하지 않고 처음부터 다시 더한다. 두 구간 `[i, j)`와 `[i+1, j)`가 대부분 겹친다는 걸 생각하면, 시작점을 하나 옮길 때 "맨 앞에서 빠지는 값 하나만 빼면" 되지 않을까 하는 생각이 든다.

## 시도 2 — 두 포인터로 창을 늘렸다 줄였다 (채택)

### 접근

오른쪽 포인터 `rt`를 하나씩 늘려 합을 키우다가, 합이 M 이상이 되면 왼쪽 포인터 `lt`를 늘려 합을 줄인다. 합이 정확히 M이 되는 순간마다(늘릴 때든 줄일 때든) 카운트한다. 원소가 모두 양수라 "늘리면 커지고, 줄이면 작아진다"가 항상 성립하므로, 합이 M을 지나치는 지점을 놓치지 않고 잡아낼 수 있다.

```java
public static int countSubarrays(int m, int[] arr) {
    int cnt = 0, sum = 0, lt = 0;
    for (int rt = 0; rt < arr.length; rt++) {
        sum += arr[rt];
        if (sum == m) cnt++;
        while (sum >= m) {
            sum -= arr[lt++];
            if (sum == m) cnt++;
        }
    }
    return cnt;
}
```

### 결과

**성공** — 예제에서 동일하게 `3` 출력.

복잡도: 시간 O(N), 공간 O(1). `lt`, `rt` 모두 0에서 `arr.length`까지만 움직이고 되돌아가지 않아, 둘을 합쳐도 전체 이동 횟수는 최대 2N이다.

### 분석

시도 1의 바깥 루프(시작점 `i`)와 안쪽 루프(끝점 `j`)를 하나의 창으로 합쳤다. `rt`가 창의 오른쪽 끝, `lt`가 창의 왼쪽 끝을 맡는다. 합이 M보다 작으면 `rt`로 창을 넓히고, M 이상이면 `lt`로 창을 좁힌다. 시도 1은 시작점마다 그 값들을 새로 더했지만, 시도 2는 창이 겹치는 동안 그 값들을 그대로 들고 있다가 왼쪽 끝이 빠질 때만 뺀다 — 이런 식으로 겹치는 값을 재사용한다. `lt`, `rt`가 둘 다 앞으로만 움직이고 뒤로 가지 않기 때문에 전체 이동이 O(N)으로 끝난다.

두 시도 모두 **원소가 양수라는 전제**에 기대고 있다. 시도 1은 "합이 M 이상이면 더 넣지 않아도 된다"는 가정에 서 있고, 시도 2는 "오른쪽으로 넓히면 합이 커지고 왼쪽을 줄이면 합이 작아진다"는 가정에 서 있다. 둘 다 원소가 음수가 아니어야 성립하는 가정이다. 배열에 음수가 섞여 있으면 값을 더하거나 뺄 때 합이 한 방향으로만 움직인다는 보장이 사라져 투 포인터를 쓸 수 없다. 이런 경우에는 **누적 합(prefix sum)과 해시맵**을 함께 써서, "지금까지의 누적 합에서 M을 뺀 값이 몇 번 나왔는지"를 세는 방식으로 풀어야 한다.

## 정리

| 시도 | 핵심 | 복잡도 | 결과 |
|---|---|---|---|
| 1. 시작점마다 다시 합산 | M 이상이면 멈추고 확인 | O(N²) 최악 | 정답, 큰 입력에서 시간 초과 우려 |
| **2. 두 포인터로 창 조절 (채택)** | 넓히다가 M 이상이면 좁힘 | O(N) | 정답, 선형 시간 |

**채택: 시도 2.** 제약(N ≤ 100,000)에서 시도 1은 최악 100억 번까지 늘어나 시간 제한이 불안하지만, 두 포인터는 각각 N번씩만 움직여 안전하게 통과한다.

- 구간을 옮기며 합이나 개수를 셀 때, **겹치는 부분을 다시 계산하지 않고 재사용**할 수 있다면 두 포인터(슬라이딩 윈도우)로 바꿀 여지가 있다.
- 이 문제의 두 풀이는 모두 **원소가 양수라는 전제**에 기대고 있다. 음수가 섞인 배열에서 같은 문제를 풀어야 한다면 투 포인터 대신 **누적 합 + 해시맵**으로 접근해야 한다.
