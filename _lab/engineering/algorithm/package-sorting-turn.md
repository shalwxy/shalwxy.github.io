## 문제

택배 터미널에는 분류 담당자가 한 명뿐이다. 상자는 들어온 순서대로 대기열에 쌓이지만, 당일배송처럼 긴급도가 높은 상자는 먼저 분류해야 한다.

그래서 터미널은 다음과 같은 방식으로 상자를 분류한다.

- 대기열 맨 앞의 상자를 하나 꺼낸다.
- 나머지 대기열에 방금 꺼낸 상자보다 긴급도가 높은 상자가 하나라도 있으면, 꺼낸 상자를 대기열 맨 뒤에 다시 넣는다. 그렇지 않으면 그 상자를 분류한다.

즉 대기열에 자신보다 긴급도가 높은 상자가 하나도 남아있지 않을 때, 비로소 자신이 분류된다.

현재 N개의 상자가 대기열에 있다. 대기열 순서대로 상자의 긴급도가 주어질 때, 대기열에서 M번째 상자(맨 앞을 0번째로 센다)가 몇 번째로 분류되는지 구한다.

- 상자 수 N(5 ≤ N ≤ 100), 구하려는 위치 M(0 ≤ M < N)
- 긴급도는 50 이상 100 이하의 정수. 같은 값이 여러 개 있을 수 있다.
- 입력: 첫 줄에 N과 M, 둘째 줄에 대기열 순서대로 상자의 긴급도
- 출력: M번째 상자가 몇 번째로 분류되는지

```
입력
5 2
63 91 77 55 88

출력
3
```

대기열은 `[63, 91, 77, 55, 88]`이다. 맨 앞 63을 꺼내보면 뒤에 91이 남아있으니 도로 맨 뒤로 보낸다. 다음으로 꺼낸 91은 남은 상자(77, 55, 88, 63) 중 더 긴급한 게 없으니 그대로 분류된다(1번째). 이후 77도 한 번 밀려났다가, 88이 2번째로 분류된 다음에야 남은 상자(55, 63) 중 더 긴급한 게 없어 3번째로 분류된다 — 그래서 2번째 상자(긴급도 77)의 답은 3이다.

## 공통 코드

아래 시도들은 입력을 읽고 결과를 출력하는 부분을 공유한다. 각 시도에서는 분류 순서를 구하는 `sortTurn` 메서드만 다르다.

```java
import java.util.Scanner;

public class Main {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        int n = sc.nextInt();
        int m = sc.nextInt();
        int[] urgency = new int[n];
        for (int i = 0; i < n; i++) urgency[i] = sc.nextInt();

        System.out.println(sortTurn(m, urgency)); // 로직은 각 시도 참고
    }
}
```

## 시도 1 — 긴급도 순으로 우선순위 큐에 몰아넣기 (실패)

### 접근

"남은 상자 중 내가 제일 긴급할 때 분류된다"는 규칙을 보고, 처음부터 긴급도가 높은 순서로 정렬해두면 그 순서가 곧 분류 순서라고 생각했다. `PriorityQueue`에 상자를 전부 넣고, 맨 앞이 내가 찾는 상자인지 확인하면서 하나씩 꺼낸다.

```java
import java.util.PriorityQueue;
import java.util.Queue;

public static int sortTurn(int m, int[] urgency) {
    Queue<Box> queue = new PriorityQueue<>(
            (a, b) -> Integer.compare(b.urgency, a.urgency)
    );
    for (int i = 0; i < urgency.length; i++) {
        queue.offer(new Box(i, urgency[i]));
    }

    int turn = 0;
    while (true) {
        turn++;
        if (queue.peek().idx == m) break;
        queue.poll();
    }
    return turn;
}

class Box {
    int idx;
    int urgency;

    public Box(int idx, int urgency) {
        this.idx = idx;
        this.urgency = urgency;
    }
}
```

### 결과

**실패** — 예제(`63 91 77 55 88`, M=2)에서는 우연히 `3`이 나와 맞지만, 긴급도가 같은 상자가 여러 개 있으면 틀린다. 예를 들어 긴급도가 `[50, 50, 50, 50, 50]`으로 전부 같을 때, 실제로는 들어온 순서대로 분류되어 1번째 상자(M=1)는 2번째로 분류되어야 한다. 하지만 이 코드는 `5`를 반환한다.

### 분석

문제의 규칙을 다시 보면, "자신보다 긴급도가 **높은**" 상자만 확인한다 — 긴급도가 **같은** 상자는 나를 가로막지 않는다. 그런데 `PriorityQueue`는 긴급도가 같은 상자들 사이의 순서를 정해주지 않는다. 내부적으로 힙 구조를 쓰기 때문에, 긴급도가 같다면 어느 상자가 먼저 나올지는 들어온 순서와 무관하게 정해진다.

더 근본적인 문제도 있다. 긴급도가 같은 두 상자 중 **어느 쪽이 먼저 분류될지는, 미리 정렬해서 알아낼 수 있는 값이 아니다.** 둘 사이에 더 긴급한 상자가 몇 개나 끼어 있다가 언제 빠져나가는지에 따라, 그때그때 달라지기 때문이다.

대기열이 `[50, 60, 50]`(차례로 idx 0, 1, 2)이라고 해보자. idx0과 idx2는 긴급도가 똑같이 50이고, 원래 대기열 순서는 idx0이 idx2보다 앞이다. 문제의 규칙을 따라가보자.

1. idx0(50)을 꺼낸다 → 뒤에 idx1(60)이 남아있으니 도로 맨 뒤로 보낸다. 대기열: `[idx1(60), idx2(50), idx0(50)]`
2. idx1(60)을 꺼낸다 → 남은 상자 중 더 긴급한 게 없으니 분류한다(1번째).
3. idx2(50)을 꺼낸다 → 남은 건 idx0(50)뿐이고 긴급도가 같아서 "더 높지" 않으니 분류한다(2번째).
4. idx0(50)을 꺼낸다 → 남은 상자가 없으니 분류한다(3번째).

결과를 보면 idx2가 2번째, idx0이 3번째로 분류됐다. 원래 대기열에서는 idx0이 idx2보다 앞에 있었는데, 정작 분류는 idx2가 먼저 된 것이다. 이유는 간단하다 — idx0은 가운데 있던 idx1(60) 때문에 한 번 더 뒤로 밀려났고, idx2는 그런 일을 겪지 않았다.

즉 동점인 두 상자 사이의 순서는 "긴급도가 같으면 원래 순서를 유지한다"처럼 고정된 규칙으로 정해지는 게 아니라, **둘 사이에 끼어 있던 더 긴급한 상자들이 몇 번이나 그 둘을 밀어냈는가**에 따라 매번 달라진다. 그래서 "전체 순서를 미리 한 번 정렬해서 고정해두는" 접근은 애초에 성립할 수 없다 — 정렬은 한 번 정해지고 끝이지만, 동점끼리의 실제 순서는 시뮬레이션이 진행되는 동안 다른 상자들에 의해 계속 바뀌기 때문이다. 규칙을 있는 그대로 흉내 내려면 "지금 남은 상자 중에 더 긴급한 게 있는가"를 매 순간 다시 확인하는 수밖에 없다.

## 시도 2 — 규칙을 그대로 흉내 내기 (채택)

### 접근

정렬로 지름길을 만들지 않고, 문제에 적힌 규칙을 코드로 그대로 옮긴다. 진짜 `Queue`에 상자를 순서대로 넣고, 맨 앞 상자를 꺼낼 때마다 **지금 남아있는 상자들만** 훑어 더 긴급한 상자가 있는지 확인한다. 있으면 맨 뒤로 다시 넣고, 없으면 분류한다.

```java
import java.util.LinkedList;
import java.util.Queue;

public static int sortTurn(int m, int[] urgency) {
    Queue<Box> queue = new LinkedList<>();
    for (int i = 0; i < urgency.length; i++) {
        queue.offer(new Box(i, urgency[i]));
    }

    int turn = 0;
    while (!queue.isEmpty()) {
        Box front = queue.poll();

        boolean hasMoreUrgent = false;
        for (Box x : queue) {
            if (x.urgency > front.urgency) {
                hasMoreUrgent = true;
                break;
            }
        }

        if (hasMoreUrgent) {
            queue.offer(front);
        } else {
            turn++;
            if (front.idx == m) return turn;
        }
    }
    return turn;
}
```

### 결과

**성공** — 예제에서 `3` 출력. 긴급도가 전부 같은 경우(`[50, 50, 50, 50, 50]`)에도 들어온 순서 그대로 1, 2, 3, 4, 5번째로 분류되어 정답과 일치한다.

복잡도: 시간 O(N²)(상자를 꺼낼 때마다 남은 대기열 전체를 훑어야 하고, 더 긴급한 상자가 남아있는 동안은 계속 다시 대기열 끝으로 밀려난다), 공간 O(N). N ≤ 100이라 충분히 빠르다.

### 분석

시도 1이 "먼저 전체 순서를 정해두고 그대로 꺼내는" 방식이었다면, 이 방식은 "지금 당장 누가 나보다 긴급한가"만 그때그때 확인한다. 긴급도가 같은 상자들 사이의 순서는 미리 정해지는 게 아니라, 대기열을 도는 동안 자연스럽게 정해진다 — 정확히 문제가 설명한 규칙 그대로다.

## 정리

| 시도 | 핵심 | 복잡도 | 결과 |
|---|---|---|---|
| 1. 미리 정렬 | 긴급도 내림차순으로 한 번에 순서 결정 | - | 동점이 있으면 실패 |
| **2. 규칙 그대로 시뮬레이션 (채택)** | 꺼낼 때마다 남은 대기열만 재확인 | O(N²) | 정답 |

**채택: 시도 2.** N이 100 이하로 작아 O(N²)이어도 충분히 빠르고, 문제의 규칙을 있는 그대로 옮긴 코드라 동점 상황에서도 안전하다.

- **각 원소가 서로를 막는 조건이 고정된 전역 규칙이 아니라, 그때그때 남아있는 대상에 따라 달라진다면**, "최종 순서를 한 번에 정렬로 정해버리는" 방식은 틀릴 수 있다. 이럴 땐 정렬 대신, 조건을 매 순간 그대로 확인하는 시뮬레이션이 안전하다.
- 동점(같은 값)을 "서로를 막지 못하는 것"으로 규칙에 명시한 문제라면, 동점끼리의 순서를 정렬의 보조키로 고정해도 맞지 않을 수 있다 — 동점끼리의 순서 자체가 시뮬레이션 과정에서 결정되기 때문이다.
