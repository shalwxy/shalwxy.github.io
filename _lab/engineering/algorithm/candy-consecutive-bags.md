## 문제

사탕 N개를 **2개 이상**의, 크기가 1씩 늘어나는 연속된 봉지들에 남김없이 나눠 담는 방법이 몇 가지인지 구한다.

- 7 ≤ N < 1,000
- 입력: 자연수 N
- 출력: 2개 이상의 연속된 자연수의 합으로 N을 나타내는 방법의 수

```
입력      출력
21        3
```

사탕 21개는 10개와 11개로 나눠 담거나(2봉지), 6, 7, 8개로 나눠 담거나(3봉지), 1, 2, 3, 4, 5, 6개로 나눠 담을 수 있다(6봉지). 이 세 가지가 전부라 답은 3.

> 출처: 인프런 [자바(Java) 알고리즘 문제풀이 입문: 코딩테스트 대비](https://www.inflearn.com/course/자바-알고리즘-문제풀이-코테대비)의 [1132번 문제](https://oj.inflearn.com/problem/1132)를 소재와 예제만 바꿔 재구성했다.

## 공통 코드

아래 시도들은 입력을 읽고 결과를 출력하는 부분을 공유한다. 각 시도에서는 방법의 수를 세는 `countWays` 메서드만 다르다.

```java
import java.util.Scanner;

public class Main {
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        int n = sc.nextInt();

        System.out.println(countWays(n)); // 로직은 각 시도 참고
    }
}
```

## 시도 1 — 평균으로 항 개수 역산

### 접근

연속된 자연수 k개의 합은 등차수열의 합이라, k개의 평균에 k를 곱하면 N이 된다. k가 홀수면 평균이 정수(가운데 항 그대로)여야 하고, k가 짝수면 평균이 "정수 + 0.5" 형태(가운데 두 항의 평균)여야 한다. k를 2부터 `N/2 + 1`까지 늘려가며 이 조건과 "첫 항이 1 이상인가"를 함께 확인했다.

```java
public static int countWays(int n) {
    int cnt = 0;
    for (int k = 2; k <= n / 2 + 1; k++) {
        double avg = (double) n / k;
        if (k % 2 == 0) {
            // 가운데 두 항의 평균 → ".5" 형태여야 함
            if (avg % 1 != 0 && avg * 2 % 1 == 0 && (int) avg - k / 2 + 1 > 0) cnt++;
        } else {
            // 가운데 항 → 정수여야 함
            if (avg % 1 == 0 && (int) avg - k / 2 > 0) cnt++;
        }
    }
    return cnt;
}
```

### 결과

**성공** — 예제에서 `3` 출력.

복잡도: 시간 O(N), 공간 O(1). k가 `N/2`까지 돌지만 N이 1,000 미만이라 어차피 넉넉하다.

식 자체는 맞지만, `avg`가 `double`이라 **부동소수점 비교**(`avg % 1 != 0`, `avg * 2 % 1 == 0`)에 의존한다.

### 분석

N과 k가 지금처럼 작을 땐 문제없이 맞아떨어지지만, 부동소수점 비교는 정확히 0.5가 나와야 할 자리에 미세한 오차가 섞일 수 있어 일반적으로는 불안하다. 거기에 짝수/홀수에 따라 조건을 따로 둬야 해서 분기도 두 겹이다. 돌이켜보면 "항이 몇 개일 때 평균이 어떤 모양이어야 하는가"를 거꾸로 따질 필요 없이, **1부터 하나씩 직접 더해보면** 같은 답을 더 단순하게 구할 수 있다.

## 시도 2 — 1부터 직접 더하며 투 포인터로 확인 (채택)

### 접근

1부터 하나씩 더해가다가(`rt`), 합이 N 이상이 되면 가장 작은 항부터 하나씩 빼낸다(`lt`). [연속 저축액 합이 M인 경우의 수](/lab/engineering/algorithm/savings-streak-sum/)와 구조가 완전히 같은데, 더하는 대상이 배열이 아니라 **1, 2, 3, …으로 이어지는 자연수 자체**라는 점만 다르다.

```java
public static int countWays(int n) {
    int cnt = 0, sum = 0, lt = 1;
    for (int rt = 1; rt <= n / 2 + 1; rt++) {
        sum += rt;
        if (sum == n) cnt++;
        while (sum >= n) {
            sum -= lt++;
            if (sum == n) cnt++;
        }
    }
    return cnt;
}
```

### 결과

**성공** — 예제에서 동일하게 `3` 출력.

복잡도: 시간 O(N), 공간 O(1). `lt`, `rt` 모두 1부터 `N/2` 안쪽까지만 움직이고 되돌아가지 않는다.

### 분석

시도 1은 "항이 k개일 때 평균이 어떤 모양이어야 하는가"를 거꾸로 따져 조건을 세웠다. 시도 2는 그 조건을 세울 필요 없이, 1부터 실제로 더해보면서 합이 N을 지나치는 순간만 잡아낸다 — [연속 저축액 합이 M인 경우의 수](/lab/engineering/algorithm/savings-streak-sum/)와 똑같이 창을 늘리다가 넘치면 줄이는 동작이고, 여기서는 "더하는 값이 1씩 커진다"는 점만 다르다. 정수 덧셈과 뺄셈만으로 끝나 부동소수점도, 짝수/홀수 분기도 필요 없다.

## 다른 방법 — 최소합을 기준으로 남는 양을 분배

시도 1의 부동소수점 비교를 정수 연산만으로 바꾸면서, 동시에 더 적은 횟수로 끝내는 방법도 있다.

"k개로 N을 만들 수 있는가"는 이렇게 바꿔 물을 수 있다. k개의 연속된 자연수를 1부터 시작해서 가장 작게 만들면 1, 2, …, k이고, 이 합(`1+2+...+k`)이 k개로 만들 수 있는 **가장 작은 값**이다. N에서 이 최소합을 빼고 남는 양을 생각해보자.

예를 들어 k=3이면 최소합은 1+2+3=6이고, N=21이면 15가 남는다. 이 15를 1, 2, 3 세 항에 똑같이 5씩 더해 밀어 올리면(1+5, 2+5, 3+5 → 6, 7, 8) 여전히 연속된 자연수이면서 합은 6+15=21로 그대로 N이 된다. 즉 "k개로 N을 만들 수 있는가"는 "**N에서 최소합을 뺀 나머지가 k로 나누어떨어지는가**"로 바뀐다. 나누어떨어지면 그 몫이 몇씩 밀어 올려야 하는지(코드의 변수로 치면 `remain / k`)를 알려준다. (반대로 k=4라면 최소합은 10, 남는 양은 11인데 11은 4로 나누어떨어지지 않으니 4개로는 21을 만들 수 없다.)

이 최소합(`1+2+...+k`)을 k가 바뀔 때마다 처음부터 다시 더하면 느리다. 핵심은 `1+2+...+k = (1+2+...+(k-1)) + k`라는 사실이다 — k까지의 최소합은 "k-1까지의 최소합에 k 하나만 더한 것"과 같다. 이전 단계의 값을 들고 있다가 k 하나만 반영하면 된다는 뜻이다.

코드는 이걸 "더하기"가 아니라 "N에서 빼기"로 뒤집어 쓴다. N=21이라면 k=2일 때 `remain`에서 2를 한 번 빼서 18(= N − (1+2))을 만들고, k=3일 때 3을 한 번 더 빼서 15(= N − (1+2+3))를 만든다. 매번 1부터 다시 더할 필요 없이, 한 단계마다 뺄셈 한 번으로 끝난다.

다만 이 누적 뺄셈은 k=2부터 시작한다(혼자인 1은 "2개 이상의 연속된 수"가 아니니 의미가 없다). 그런데 최소합 `1+2+...+k` 자체는 1부터 시작하므로, `1 + (2+3+...+k)`로 쪼개서 **1만 미리 떼어놓고** 나머지(`2+3+...+k`)만 루프에서 k=2부터 누적해서 뺀다. 그래야 `remain`이 항상 "N에서 그 시점까지의 최소합을 뺀 나머지"와 정확히 같아진다.

```java
public static int countWays(int n) {
    int cnt = 0;
    int remain = n - 1; // 최소합의 "1"을 미리 떼어 둔 나머지
    for (int k = 2; remain > 0; k++) {
        remain -= k; // 누적하면 remain = n - (1+2+...+k)
        if (remain >= 0 && remain % k == 0) cnt++;
    }
    return cnt;
}
```

복잡도: 시간 O(√N), 공간 O(1). `remain`이 k가 커질수록 더 큰 값만큼 줄어들어(2, 3, 4, …씩), k가 약 √(2N)에 이르기 전에 0 이하가 되어 루프가 끝난다 — 시도 1, 2의 O(N)보다 적은 횟수로 끝난다.

N이 1,000 미만인 지금은 체감되지 않지만, N의 범위가 훨씬 커진다면 이쪽이 유리하다. 다만 "왜 1을 미리 떼어놓는가"를 이해하려면 최소합 공식을 거쳐야 해서, 투 포인터보다 읽는 데 한 단계가 더 필요하다.

## 정리

| 시도 | 핵심 | 복잡도 | 결과 |
|---|---|---|---|
| 1. 평균으로 역산 | 평균의 형태(정수/.5)로 판정 | O(N) | 정답, 부동소수점 비교에 의존 |
| **2. 투 포인터로 직접 확인 (채택)** | 1부터 더하고 빼며 확인 | O(N) | 정답, 정수 연산만 사용 |
| 다른 방법. 최소합 기준 분배 | 최소합을 뺀 나머지가 k로 나누어떨어지는지 확인 | O(√N) | 정답, 가장 빠르지만 이해에 한 단계 더 필요 |

**채택: 시도 2.** 시도 1, 다른 방법과 복잡도 차이가 체감되지 않는 제약(N < 1,000)에서는, 수식을 거치지 않고 바로 읽히는 투 포인터가 가장 단순하다.

- "항이 몇 개일 때 조건을 만족하는가"처럼 거꾸로 따지는 식이 떠오르면, **직접 더해보면서 범위를 좁혀가는 투 포인터**로 바꿀 수 있는지부터 확인해본다. 부동소수점 비교를 피할 수 있는 경우가 많다.
- 같은 정답이라도 "최소 구성"을 기준으로 놓고 나머지를 분배할 수 있는지 보면, 전체를 다 훑지 않고도(O(√N)) 답을 구할 수 있는 경우가 있다. 다만 그 수식을 이해하는 비용이 늘어나니, 제약이 넉넉하면 더 직관적인 쪽을 채택하는 게 낫다.
- 투 포인터는 배열 위에서만 동작하는 기법이 아니다. "다음 값"을 규칙으로 만들어낼 수 있다면(여기서는 `rt + 1`), 배열 없이도 똑같이 쓸 수 있다.
