## 문제

**정책**이라는 말은 몇 가지를 뭉뚱그린다.

- **호출 제한**(rate limit): 지갑 주소당 초당 호출 횟수 제한
- **접근 제어**(ACL): 특정 IP는 특정 엔드포인트를 못 씀
- **화이트리스트·블랙리스트**: 이 지갑은 수수료 면제, 저 지갑은 출금 금지
- **feature flag**: "A 기능 켜기/끄기"를 코드 배포 없이
- **lockout**: 로그인 실패가 반복되면 일정 시간 잠금

공통점은 **"비즈니스 로직이 아니라 제어 로직"**이라는 점이다. 거래 처리 자체와는 다른 축에서 "할 수 있는가, 얼마나 할 수 있는가"를 결정한다.

문제는 이 로직이 **여러 서비스에 흩어져 있었다**. 호출 제한은 **공통 라이브러리**에 코드로, 블랙리스트는 **계정 서비스**의 테이블에, 화이트리스트는 **블록체인 서비스**의 테이블에, feature flag는 **각 서비스가 메모리에 올려 두고 읽는** 식으로.

같은 결정("이 사용자가 이 요청을 할 수 있나?")을 하는 곳이 많아 **정책 변경이 여러 서비스를 거쳐야 했고**, 각자 **같은 정책을 다르게 해석**할 위험이 있었다.

## 시도 1 — 기존 서비스에 모두 흡수

### 접근

가장 큰 서비스(**포털 서비스**)로 제어 로직을 다 옮긴다. 계정·블록체인 서비스와 공통 라이브러리의 정책 코드·테이블을 가져온다.

```
포털 서비스
├── 사용자 프로필
├── 콘텐츠 관리
├── 알림 설정
├── … (기존 콘텐츠 도메인)
├── rate limit (← 공통 라이브러리에서 가져옴)
├── blacklist/whitelist IP (← 계정 서비스에서)
└── feature flag (← 각 서비스에서)
```

### 결과

**부분 성공** — 흩어진 코드가 한 자리에 모였다. 하지만 **콘텐츠 도메인과 제어 도메인이 한 서비스 안에 섞여** 다음 문제가 났다.

- **서비스가 커지고 배포가 무거워진다** — 콘텐츠 기능 하나 수정해도 정책 부분까지 같이 배포된다.
- **책임 경계가 흐려짐** — "이 서비스는 뭘 하는 서비스인가?"에 대답하기 어려워진다. 콘텐츠? 정책? 둘 다?
- **다른 서비스가 정책을 조회할 때 포털 서비스로 호출이 몰림** — 포털 서비스의 응답 지연이 정책 조회 지연이 된다. 포털 서비스 장애가 **모든 서비스의 정책 검사 실패**로 번진다.

### 분석

**"흩어져 있는 것을 모으는 것"과 "모은 것을 다른 것과 섞는 것"은 다르다.** 모은다는 아이디어는 맞았지만, **모을 장소**가 "기존에 큰 서비스"면 안 됐다. 그 서비스의 **원래 책임이 희석**된다.

정책은 **자기 도메인**을 가진 축이다 — 사용자·콘텐츠·거래와 교차하지만 어느 쪽에도 속하지 않는다. 그렇다면 **자기 서비스**를 가져야 한다.

## 시도 2 — 정책 전용 서비스를 새로 만듦 (채택)

### 접근

**정책 전용 서비스**를 새로 하나 만든다. 이름은 "policy"·"guard"처럼 "제어"의 뉘앙스를 주는 일반명으로.

```
정책 서비스
├── rate limit
├── blacklist / whitelist (IP, 지갑, 이메일 등)
├── feature flag
├── lockout
└── (추가) 출금 화이트리스트
```

다른 서비스는 정책 서비스에 **"이 요청을 허용해도 되나?"**를 묻는다.

```go
// 블록체인 서비스에서 출금 요청을 받을 때
allowed, err := policyClient.CheckWithdrawal(ctx, &CheckRequest{
    WalletAddress: addr,
    Amount:        amount,
})
if !allowed.IsAllowed {
    return ErrPolicyDenied
}
// 통과 → 실제 출금 처리
```

### 결과

**성공** — 세 가지가 동시에 좋아진다.

**① 정책 변경이 한 자리에서 끝난다.** 새 규칙 추가, 정책 값 수정, feature flag 토글 — 모두 정책 서비스 한 곳만 건드린다.

**② 각 서비스가 "자기 일"에 집중한다.** 계정 서비스는 계정만, 블록체인 서비스는 블록체인만. 제어 로직을 신경 쓸 필요가 없다 — RPC 하나로 "허용?"만 묻는다.

**③ 정책 메모리 문제 해결.** 처음에는 각 서비스가 정책 전체를 메모리에 올려 두고 로컬에서 판단했다 — 서비스 수 × 정책 크기만큼 메모리를 썼다. 정책 서비스로 모으면서 **한 곳에서만** 메모리에 올려 두도록 바꿨다. 다른 서비스는 캐시된 RPC 응답만 짧게 들고 있는다.

### 분석 — "모을 곳"은 새 서비스여야 한다

모을 때 고려한 선택지는 셋이었다.

| 안 | 장점 | 단점 |
|---|---|---|
| 공통 라이브러리에 둠 (원래 구조) | 호출 비용 없음 | 배포 때마다 모든 서비스 재빌드. 정책 변경이 코드 변경과 섞임 |
| 기존 서비스(포털)에 흡수 | 새 인프라 불필요 | 콘텐츠 도메인과 섞여 책임 경계 흐려짐. 서비스 비대화 |
| **정책 전용 서비스 (채택)** | 책임 경계 분명, 독립 배포, 메모리 분산 | RPC 호출 비용, 서비스 하나 추가 |

세 번째는 운영 부담이 늘어나지만 **"정책은 자기 도메인"**이라는 설계상의 정직함이 있다. 콘텐츠·거래·사용자가 각자 서비스인 것과 같은 레벨에서 정책도 서비스여야 한다.

### 통합의 순서

한번에 "모두 옮기기"는 위험하다. 정책이 거는 요구는 서비스마다 조금씩 다르고, 옮기면서 **"어떤 축으로 통합할까"**를 발견하게 된다. 아래 순서로 갔다.

1. **기초 기능부터** — rate limit · blacklist/whitelist IP · feature flag
2. **새 기능 추가** — lockout 정책 (신규라 기존 코드와 섞일 일 없음)
3. **마지막에 도메인 특수 기능** — 블록체인 서비스의 출금 화이트리스트 이관

마지막이 어려운 이유는 **"출금 화이트리스트"가 블록체인 도메인 지식을 쓰기 때문**이다 — 지갑 주소 체크섬, 토큰 종류별 한도 등. 선택은 두 가지였다. 정책 서비스에 이 지식을 넣을지, 아니면 정책 서비스는 "ID만 보는 범용 whitelist"로 두고 블록체인 서비스가 매핑을 하게 할지. 결국 **"정책 서비스는 ID 기반 범용 whitelist, 블록체인 서비스가 지갑 주소 ↔ ID 변환"**으로 나눴다.

통합을 서두르지 않고 **각 도메인 지식이 어느 쪽에 속해야 하는지**를 한 기능씩 결정하는 게 낫다.

### 운영에서 발견한 이슈들

**Redis 정밀도.** rate limiter를 sliding window 방식으로 구현했는데, Redis Lua의 `tonumber`가 큰 timestamp를 float로 변환하면서 **정밀도가 소실**됐다. 그 결과 카운터 로직에 오류가 있었다. `tostring` 유지 또는 정수 연산으로 바꿔 해결.

**메모리 압박.** rate limit 정책을 **모든 호출 서비스가 각자 메모리에 refresh**하던 초기 구조에서 OOM에 가까운 상황이 있었다. 정책 refresh 역할을 **정책 서비스 한 곳으로** 옮겨 메모리 압박을 줄였다.

**관리자 블록 처리.** 자동 lockout과 수동 블록(관리자가 직접)이 같은 테이블을 썼는데, 둘의 해제 로직이 뒤섞이는 버그가 있었다. **블록의 origin**(자동/관리자)을 구분해 각자 독립적으로 해제되도록 처리했다.

### 캐시와 jitter

정책 서비스가 병목이 되지 않으려면 **각 서비스가 응답을 짧게 캐시**해야 한다. 여기에 **jitter**(캐시 만료 시간에 랜덤 ±α)를 더해, 수십 개 서비스가 **동시에 캐시를 refresh**하지 않게 한다. ([jitter 글 참고](/lab/engineering/distributed/policy-refresh-with-jitter/))

## 다른 방법 — 사이드카 / 게이트웨이 수준에서 처리

정책을 **애플리케이션 서비스가 아닌 인프라 수준**에서 처리하는 방법도 있다.

- **API 게이트웨이** (Envoy, Kong)에 rate limit · IP ACL · auth 정책을 넣는다
- **서비스 메시 사이드카** (Istio, Linkerd)에서 정책을 enforce
- **OPA** (Open Policy Agent) 같은 전용 정책 엔진을 사이드카로

- 얻는 것: 애플리케이션 코드와 분리. 정책 변경이 설정 파일만 바꾸면 된다.
- 치르는 것: **비즈니스 로직과 결합된 정책**(예: "이 지갑의 토큰 종류별 한도 확인")은 게이트웨이가 모른다. 게이트웨이 설정이 복잡해지고, 결국 애플리케이션 서비스로 돌아간다.
- **단순한 네트워크 수준 정책**(IP 차단, 호출 제한의 총량)은 게이트웨이가 맞다. **비즈니스 지식이 필요한 정책**(토큰별 한도, 사용자 등급별 접근권한)은 전용 서비스가 맞다.

둘을 섞어 쓰는 것도 가능하다 — 게이트웨이가 1차 필터링(IP 차단, 총량 제한), 전용 서비스가 2차 판단(비즈니스 규칙).

## 정리

| 방식 | 책임 경계 | 변경 비용 | 적합한 자리 |
|---|---|---|---|
| 공통 라이브러리 | 코드에 결합 | 서비스 재빌드·재배포 필요 | 변경이 드물고 단순한 정책 |
| 기존 서비스에 흡수 | 모호 | 콘텐츠 변경과 섞임 | 임시 통합, 과도기 |
| **정책 전용 서비스 (채택)** | 분명 | 한 자리에서 수정·배포 | 정책이 여러 서비스에 걸치고 자주 바뀔 때 |
| 다른 방법. 게이트웨이/사이드카 | 인프라와 결합 | 설정만 수정 | 네트워크 수준 정책 |

**채택: 시도 2.** 흩어진 제어 로직을 모을 때 **"기존 큰 서비스에 넣는 것"**이 아니라 **"자기 서비스를 주는 것"**이 책임 경계를 지킨다. 콘텐츠·거래와 동급의 도메인으로 다루고, 비즈니스 서비스는 RPC로 묻기만 한다.

- 같은 결정을 하는 코드가 **여러 서비스에 흩어져** 있다면, 그 결정은 **자기 서비스**를 가질 자격이 있다. 모을 때 기존 큰 서비스에 넣으면 안 된다.
- 통합은 **한 번에 하지 말고** 기능별로. 각 기능이 어떤 도메인 지식을 쓰는지 보면서 "정책 서비스에 둘 것"과 "원래 서비스에 남길 것"을 나눈다.
- 정책 서비스가 병목이 되지 않으려면 **호출 쪽에 짧은 캐시 + jitter**. 메모리는 정책 서비스에만 두고, 호출 서비스는 응답만 캐시한다.
- 네트워크 수준 정책(IP · 총량)은 **게이트웨이**에, 비즈니스 수준 정책은 **전용 서비스**에. 둘을 섞어 쓰는 게 자연스럽다.
