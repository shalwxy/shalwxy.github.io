## 문제

보안 기능 하나. **이메일을 바꾸면 그 시점부터 일정 시간**(예: 24시간) **보안 설정을 바꿀 수 없다.** 탈취된 계정으로 이메일을 바꾼 공격자가 바로 OTP·비밀번호·결제 정보를 바꾸지 못하도록 막는 장치다.

"잠금"이라는 단어 때문에 **Redis TTL**이 자연스러워 보였다 — 이메일 바꿀 때 키를 걸고, TTL이 만료되면 알아서 사라진다. 코드가 짧다.

```go
// 이메일 변경 시
redis.Set(ctx, "security_lock:"+userID, "1", 24*time.Hour)

// 보안 설정 변경 시
locked, _ := redis.Exists(ctx, "security_lock:"+userID)
if locked { return ErrLocked }
```

이 코드가 **세 가지**로 깨졌다.

## 시도 1 — Redis TTL로 잠금

### 접근

위 코드 그대로. 이메일 변경 시 `SET key value EX 86400`, 보안 설정 변경 시 `EXISTS key`.

### 결과

**실패** — 다음 세 가지가 차례로 걸렸다.

**① 잠금 기간을 바꿔도 이미 생긴 키엔 반영 안 됨.** 운영이 "24시간 → 72시간"으로 정책을 바꾸면, **그 시점 이후에 생긴 키만** 72시간이 된다. 이미 어제 이메일을 바꾼 사용자는 여전히 24시간 TTL을 쓴다. "정책이 바뀌었으니 전원 소급 적용"이 불가능하다. 반대로 기간을 줄여도 기존 키는 그대로 오래 유지된다.

**② Redis가 재시작되면 잠금이 사라진다.** AOF·RDB 설정에 따라 다르지만, 완전 영속은 아니다. 공격자가 이메일을 바꾼 뒤 Redis 장애·재시작을 틈타 보안 설정을 바꿀 수 있다 — **보안 기능인데 영속성이 약함.**

**③ TTL 설정이 "0" 또는 "비활성화"인 상황을 다루기 어려움.** 운영에서 "당분간 잠금 끄기"가 필요한 경우가 생겼다. Redis 쪽은 "키를 아예 안 만드는 분기"를 서비스 코드에 넣어야 하는데, 이 분기와 조회 분기가 서로 다른 자리에 있어 실수하기 쉽다.

### 분석

이 문제들은 **구현 버그가 아니라 Redis TTL이 "잠금"을 표현하는 방식의 한계**다.

- Redis TTL은 **키가 생길 때** 결정된다. 정책 변경이 소급되지 않는다.
- Redis는 메모리 기반이라 **영속성이 약하다.** 중요한 상태는 RDB·AOF가 있어도 영구 보장이 아니다.
- "잠금"의 의미가 **"지금 잠겨 있나"**라는 **boolean**인데, 사실 비즈니스 요구는 **"특정 시각 이후 얼마나 지났나"**라는 시간 계산이다.

마지막 줄이 가장 중요하다. 비즈니스 규칙을 다시 적어 보면 "**이메일 변경 시각 + 잠금 기간 > 지금** 이면 잠겨 있음". 이건 TTL이 아니라 **시각의 저장과 비교**로 적는 게 자연스럽다.

## 시도 2 — DB 컬럼에 "변경 시각" 저장 (채택)

### 접근

**이메일 변경 시각**(`email_changed_at`)을 DB 컬럼으로 추가하고, 보안 설정 변경 시 `email_changed_at + lock_duration > NOW()`로 판단한다. `lock_duration`은 서비스 설정에서 읽는다.

```sql
ALTER TABLE accounts ADD COLUMN email_changed_at TIMESTAMPTZ;
```

```go
// 이메일 변경 시 — 시각만 기록
db.Exec("UPDATE accounts SET email = $1, email_changed_at = NOW() WHERE id = $2", newEmail, userID)

// 보안 설정 변경 시 — 경과 시간 계산
account := db.QueryAccount(ctx, userID)
lockUntil := account.EmailChangedAt.Add(s.config.SecurityLockDuration)
if time.Now().Before(lockUntil) {
    return ErrLocked
}
```

### 결과

**성공** — 세 문제가 동시에 사라졌다.

**① 정책 변경이 즉시 반영된다.** `SecurityLockDuration`을 24h → 72h로 바꾸면 **이미 이메일을 바꾼 사용자도** 새 기준으로 판정된다(어제 바꾼 사람이 아직 24h가 안 지났으면 이제 72h 기준으로 다시 봐야 함). 소급 적용이 공짜다.

**② 영속성이 보장된다.** DB는 영속 저장소다. 서버가 재시작되어도 `email_changed_at`은 그대로다.

**③ 비활성화가 자연스럽다.** `SecurityLockDuration = 0`이면 `email_changed_at + 0 > NOW()`가 항상 false라(변경 시각은 늘 과거다), 잠금이 걸리지 않는다. 설정 하나로 기능을 끌 수 있다.

### 분석 — "잠금"이라는 단어에 속지 않기

처음에 Redis TTL을 떠올린 이유는 **"잠금"이라는 단어**였다. 잠금 = TTL = Redis. 이 연상이 자연스러워 보여서 요구사항을 재구성하지 않았다.

다시 적어 보면 요구는 **"어떤 사건의 발생 시각으로부터 N시간 동안은 다른 사건을 막는다"**이다. 이걸 그대로 번역하면:

- **사건의 발생 시각** → DB 컬럼 `event_at TIMESTAMPTZ`
- **N시간** → 서비스 설정 (환경별 변경 가능)
- **막는다** → `event_at + N > NOW()`일 때 거절

이 모델은 "잠금"이 아니라 **"쿨다운(cooldown)"**에 가깝다. 쿨다운 패턴은 게임의 스킬 재사용 대기시간, API 레이트 리미트의 재시도 금지, 비밀번호 변경 후 다음 변경까지의 금지 기간 — 전부 같은 모양이다. 모두 "시각을 저장하고 경과를 계산한다" 하나로 해결된다.

### 세부 — 조회 하나를 어떻게 줄였는가

구현 과정에서 세 가지 작은 결정이 더 있었다.

**① 응답 필드 추가로 호출 하나 줄이기.** 처음엔 "잠금 확인" 전용 API(`GET /security/lock-status`)를 따로 만들었다. 프론트가 보안 설정 페이지에 들어갈 때마다 이 API를 한 번 더 호출한다. 그러면 네트워크 왕복이 하나 는다.

대신 **이미 호출하는 사용자 정보 응답(`GET /users/me`)에 `security_lock_until` 필드**를 하나 추가했다. 프론트는 추가 호출 없이 잠금 종료 시각을 알 수 있다.

```json
GET /users/me
{
  "id": "...",
  "email": "...",
  "security_lock_until": "2026-10-01T12:00:00Z"   // 지나면 null
}
```

API를 **늘리는 대신 기존 응답의 필드 하나로** 합치는 습관은 호출 수·지연·유지보수 모두에 좋다.

**② 복제 지연 피하기.** DB가 Primary·Replica 구성이면, 이메일을 Primary에 쓴 직후 Replica에서 조회하면 **옛 값이 보일 수 있다**(수백 ms~수 초의 복제 지연). 사용자가 이메일을 바꾸고 바로 보안 설정 페이지를 열면 잠금이 안 걸린 것처럼 보일 수 있다.

이 경로만 **Primary에서 직접 조회**하도록 바꿨다. 같은 서비스 안에서 라우팅을 분리하는 설정이면 충분하다.

**③ 설정이 0이면 조회 자체를 생략.** `SecurityLockDuration == 0`일 때 DB 조회를 하지 않도록 서비스 상단에서 분기. 불필요한 쿼리를 아끼고, 설정만으로 기능 전체를 끌 수 있다.

```go
if s.config.SecurityLockDuration == 0 {
    return nil   // 잠금 기능 비활성화
}
account := db.QueryAccount(...)
// ...
```

## 다른 방법 — 전용 이력 테이블

단순한 "마지막 변경 시각"으로 부족한 경우 — 예를 들어 **어떤 변경인지 종류를 기록**하고 싶거나, **누가·언제·어디서 바꿨는지**까지 남겨야 하면, 별도 **이력 테이블**을 둔다.

```sql
CREATE TABLE security_events (
    id UUID PRIMARY KEY,
    account_id UUID NOT NULL,
    event_type VARCHAR NOT NULL,   -- EMAIL_CHANGED, PASSWORD_CHANGED, OTP_RESET 등
    occurred_at TIMESTAMPTZ NOT NULL,
    actor VARCHAR,                 -- user, admin, system
    ip_address INET,
    user_agent TEXT
);

CREATE INDEX idx_security_events_latest
  ON security_events (account_id, event_type, occurred_at DESC);
```

잠금 판정은 **가장 최근 보안 이벤트의 시각**을 조회해서 같은 방식으로 계산한다.

- 얻는 것: **여러 이벤트 종류**를 통일된 모델로 담는다. 감사 로그와 자연히 연결된다.
- 치르는 것: 컬럼 하나로 끝나는 단순 케이스엔 과하다.
- **감사·추적이 중요한 보안 기능**이면 이쪽을 처음부터 쓴다. 이 글의 케이스는 "이메일 변경"만 다루면 됐으므로 컬럼으로 충분했지만, 2년 뒤 "보안 이벤트 전반을 추적" 요구가 들어오면 이력 테이블로 승격한다.

## 정리

| 방식 | 영속성 | 정책 변경 반영 | 적합한 자리 |
|---|---|---|---|
| Redis TTL | 약함 | 신규 키부터 적용 | **서비스 전역의 실시간 쿨다운**(초·분 단위), 분산 락 |
| **DB 컬럼 (채택)** | 강함 | 즉시 전원 | 사용자별로 영속되어야 하는 "~이후 N시간" 규칙 |
| 다른 방법. 이력 테이블 | 강함 | 즉시 전원 | 감사·추적까지 필요한 보안 이벤트 |

**채택: 시도 2.** "~시점 이후 N시간 동안 X" 같은 규칙은 **잠금이 아니라 쿨다운**이고, 쿨다운은 "**시각 저장 + 경과 계산**"으로 가장 자연스럽게 모델링된다. Redis TTL은 정책 변경 미반영과 영속성 약함이 두 큰 함정이다.

- "잠금"이라는 단어가 들리면 **Redis TTL을 먼저 떠올리지 말고**, 비즈니스 규칙을 다시 적어 본다. "~이후 N시간"이라면 쿨다운이고, DB 컬럼이 맞다.
- 정책 변경이 **"이미 걸린 잠금에도 적용"**되어야 하면 TTL은 피한다. TTL은 키 생성 시점에 고정된다.
- 보안 기능의 상태는 **영속 저장소**에 둔다. 메모리 기반 저장소의 재시작으로 보안 보장이 깨지면 안 된다.
- 잠금 여부를 묻는 **별도 API보다 기존 응답의 필드 하나**로. 호출 수와 지연이 모두 줄어든다.
- Primary·Replica 구성이면, 방금 쓴 값이 바로 읽혀야 하는 경로는 **Primary 조회**로 분리한다.
