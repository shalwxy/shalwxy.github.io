## 문제

거래소 BFF에 **북마크 목록 조회** 캐시를 넣었다. 사용자가 한 지갑의 북마크를 조회하면 응답을 Redis에 올려 두고, 같은 요청이 다시 오면 캐시에서 돌려준다.

```go
func (s *BookmarkService) List(ctx, walletAddr) ([]Bookmark, error) {
    return cache.GetOrFetch(ctx, "bookmarks:"+walletAddr, 60*time.Second, func() ([]Bookmark, error) {
        return bookmarkClient.List(ctx, walletAddr)
    })
}
```

이걸로 사용자 쪽은 빨라졌는데, 다음 문제가 생겼다 — **북마크/언북마크 요청이 들어오면 캐시가 옛 값**이라 사용자가 "내가 방금 북마크했는데 안 보여요" 라는 CS를 냈다.

TTL이 60초라, 추가/삭제 직후 최대 60초 동안 옛 목록이 보였다.

## 시도 1 — 쓰기 때 캐시 즉시 지우기

### 접근

북마크·언북마크 성공 후 캐시를 바로 지운다. 다음 조회는 캐시 미스가 나고 신선한 값을 다시 채운다.

```go
func (s *BookmarkService) Add(ctx, walletAddr, itemID) error {
    if err := bookmarkClient.Add(ctx, walletAddr, itemID); err != nil {
        return err
    }
    cache.Delete(ctx, "bookmarks:"+walletAddr)   // ← 캐시 무효화
    return nil
}
```

### 결과

**부분 성공** — 기능적으로는 맞지만, **쓰기 응답 시간이 늘어난다.** 북마크 추가 1회에 외부 호출이 2번(북마크 RPC 1회 + Redis 캐시 삭제 1회) 생겼다. 사용자 체감은 크지 않지만, 북마크가 몰릴 때 Redis 부하가 올라갔다.

더 중요한 건, **삭제 자체가 실패할 수 있다**는 점이다. Redis 일시 장애·네트워크 지연이 나면 캐시가 안 지워지고, 로그엔 "북마크는 성공, 캐시 삭제 실패"로 남는다. 사용자 눈엔 북마크가 안 보인다.

### 분석

쓰기 응답 시간에 "사용자가 기다릴 필요 없는 작업"(캐시 삭제)이 끼어 있다. 이걸 **쓰기 응답 바깥**으로 빼면 응답이 빨라지고 Redis 실패도 사용자 응답과 분리된다.

## 시도 2 — 캐시 삭제를 비동기로

### 접근

`go` 키워드(Go의 고루틴)로 캐시 삭제를 비동기 실행한다.

```go
func (s *BookmarkService) Add(ctx, walletAddr, itemID) error {
    if err := bookmarkClient.Add(ctx, walletAddr, itemID); err != nil {
        return err
    }
    go cache.Delete(ctx, "bookmarks:"+walletAddr)   // ← 비동기
    return nil
}
```

### 결과

**실패** — 사용자가 여전히 옛 캐시를 본다는 리포트가 들어왔다. 로그를 보니 `context canceled` 에러가 뜨고 있었다.

### 분석

`go func() { cache.Delete(ctx, ...) }()`에서 **`ctx`가 요청 처리의 context**였다. 요청이 끝나는 순간(응답을 돌려준 직후) context가 취소되고, 아직 실행 중이던 캐시 삭제도 같이 취소된다. 운이 좋으면 삭제가 context 취소 전에 끝나고, 운이 나쁘면 취소된다.

"비동기로 뒤에서 처리한다"는 아이디어는 맞았는데, **context의 생명주기**를 잘못 썼다. 요청 context에 묶인 작업은 요청이 끝나면 끝난다.

## 시도 3 — context를 분리

### 접근

`context.WithoutCancel` 또는 `context.Background()`로 새 context를 만들어 넘긴다. 혹시 느린 Redis를 기다려야 하나 싶어 지연도 10초·30초·1분으로 늘려 봤다.

```go
go func() {
    newCtx, cancel := context.WithTimeout(context.Background(), 1*time.Minute)
    defer cancel()
    cache.Delete(newCtx, "bookmarks:"+walletAddr)
}()
```

### 결과

**실패** — 삭제가 간헐적으로 실패하는 비율이 여전히 있었다. Redis 장애든, 네트워크 지연이든, 서버 재시작이든, **"쓰기 뒤에 캐시를 지우는 비동기 작업"**은 이 모든 실패에 노출된다.

### 분석

문제의 본질이 context가 아니라 **"쓰기와 캐시 삭제를 묶는 것 자체"**라는 걸 깨달았다.

| 묶는 방식 | 깨지는 지점 |
|---|---|
| 동기 삭제 | 삭제가 느리면 사용자 응답이 느려짐 |
| 비동기 (요청 context) | 요청 끝날 때 취소됨 |
| 비동기 (분리 context) | Redis·네트워크 장애에 노출, 서버 크래시 시 소실 |
| 아웃박스 패턴으로 재시도 보장 | 구조가 무거워짐, 캐시 하나 때문에 큰 프레임워크 |

**어떤 방식이든 "쓰기 측에서 캐시를 정확히 지우기"는 무료가 아니다.** 지우는 것을 보장하려면 캐시 하나를 위해 메시지 큐·아웃박스까지 들여와야 한다. 북마크 조회의 중요도에 비해 비용이 과하다.

## 시도 4 — 지우지 않고 짧은 TTL로 (채택)

### 접근

캐시 삭제를 **전부 제거**하고, TTL을 **3초**로 줄였다. 쓰기 쪽 코드는 캐시를 전혀 건드리지 않는다.

```go
func (s *BookmarkService) List(ctx, walletAddr) ([]Bookmark, error) {
    return cache.GetOrFetch(ctx, "bookmarks:"+walletAddr, 3*time.Second, func() ([]Bookmark, error) {
        return bookmarkClient.List(ctx, walletAddr)
    })
}

func (s *BookmarkService) Add(ctx, walletAddr, itemID) error {
    return bookmarkClient.Add(ctx, walletAddr, itemID)
    // 캐시 삭제 코드 없음
}
```

### 결과

**성공** — 쓰기 코드가 단순해지고, 삭제 실패라는 상태가 애초에 없다. 북마크 후 최대 3초 동안 옛 목록이 보일 수 있는데, 그 정도 지연은 UX상 문제가 되지 않았다.

### 분석 — "지우지 않기"가 왜 가장 싼가

세 가지가 동시에 좋아진다.

**① 쓰기 경로가 단순해진다.** 북마크 추가·삭제 코드는 자신의 일(DB 쓰기)만 한다. 캐시는 자기 TTL로 알아서 만료되므로, 쓰기 쪽이 "지웠는지 확인하는 책임"에서 해방된다.

**② 실패 모드가 줄어든다.** 캐시 삭제는 Redis·네트워크·서버 생명주기에 다 노출되는 일이었다. 그걸 없애면 "**쓰기는 성공했는데 캐시 삭제가 실패해서 사용자가 옛 값을 본다**"라는 상태 자체가 사라진다. TTL은 Redis가 알아서 처리한다.

**③ 쓰기·읽기 코드가 분리된다.** 캐시 무효화는 **쓰기 쪽이 읽기 쪽의 사정을 알아야** 가능하다("북마크 추가는 어떤 캐시 키를 지워야 하지?"). 짧은 TTL은 **읽기 쪽만의 결정**이다. 쓰기는 자기 작업만 하면 된다.

### 트레이드오프를 어떻게 결정하나

"최대 3초 옛 값"이 허용되는지는 **데이터의 성격**에 달렸다.

| 데이터 | 옛 값이 보이면? | 짧은 TTL이 맞나? |
|---|---|---|
| 북마크 목록 | 자기가 방금 추가했는데 안 보임 | 몇 초면 괜찮음 |
| 재고 수량 | "품절"이 "재고 1개"로 보임 | 안 됨. 무효화 또는 단일 진실 소스 |
| 결제 상태 | "결제 완료"가 "결제 중"으로 보임 | 안 됨. 무효화 필요 |
| 상품 카테고리 | 어제 바꾼 카테고리가 오늘 아침까지 안 반영 | 긴 TTL(수 분~수 시간)이면 충분 |
| 사용자 프로필 (닉네임·아바타) | 바꿨는데 다른 자리에서 옛값 | 수십 초면 괜찮음 |

"옛 값이 보이는 비용"과 "무효화를 보장하는 비용"을 비교해서 **싼 쪽을 고른다.** 북마크 목록은 전자가 작고 후자가 크므로 짧은 TTL이 맞다. 결제 상태는 그 반대다.

### TTL 길이를 어떻게 정하나

3초는 두 가지 중간이다 — **너무 길면 UX가 깨지고, 너무 짧으면 캐시가 거의 도움이 안 된다.**

- 북마크 목록 조회가 많이 들어오는 자리는 동일 사용자가 **몇 초 안에 반복 조회**하는 패턴이 있었다. 3초면 그 안의 반복은 캐시로 처리되고, 그 뒤 조회는 신선한 값을 받는다.
- 트래픽 특성에 따라 1초·5초·10초가 될 수도 있다. **동일 키의 조회 간격**을 로그로 측정해서 "그 간격의 몇 배"로 잡으면 맞춘다.

## 다른 방법 — 아웃박스 + 캐시 무효화 메시지

쓰기 쪽이 캐시 삭제를 **반드시 보장**해야 하는 데이터라면, 삭제 작업을 **같은 트랜잭션의 outbox 테이블에 기록**하고 별도 워커가 캐시를 지운다.

```go
db.Transaction(func(tx) error {
    tx.Insert(bookmark)
    tx.Insert(outbox, Message{Type: "cache_invalidate", Key: "bookmarks:" + walletAddr})
    return nil
})
```

- 얻는 것: 쓰기가 commit되면 outbox도 같이 commit된다. 워커가 outbox를 읽어 캐시를 지우고, 실패하면 재시도한다. **"쓰기는 성공했는데 캐시 삭제가 안 됨"이 영구적으로 남지 않는다.**
- 치르는 것: outbox 테이블, 워커 인프라, 재시도·중복 처리 — 전체 시스템이 무거워진다.
- **옛 값이 보이는 비용이 크고**(결제·재고 등), **쓰기 지연은 받아들일 수 없는** 데이터에 쓴다. 북마크는 아니었다.

## 정리

| 방식 | 쓰기 코드 | 캐시 정확성 | 적합한 자리 |
|---|---|---|---|
| 동기 삭제 | 느려짐 | 거의 즉시 | 쓰기가 드문 중요 데이터 |
| 비동기 삭제 (요청 context) | 빠름 | 자주 깨짐 | — (피해야 함) |
| 비동기 삭제 (분리 context) | 빠름 | 가끔 깨짐 | 캐시가 핵심 아님 |
| **짧은 TTL (채택)** | 캐시 코드 없음 | 최대 TTL만큼 지연 | 옛 값이 수 초 보여도 괜찮은 데이터 |
| 다른 방법. 아웃박스 | 트랜잭션에 포함 | 보장됨 (결과 일관성) | 옛 값이 보이면 안 되는 중요 데이터 |

**채택: 시도 4.** 북마크 목록처럼 **옛 값이 몇 초 보여도 사용자 피해가 없는** 데이터는, 캐시 무효화를 시도하지 말고 **TTL이 알아서 만료되게** 두는 쪽이 코드·실패·운영 모두 싸다.

- "캐시 무효화가 실패한다"는 패턴을 발견하면, **무효화를 보장하려는 방향** 대신 **옛 값이 보여도 괜찮게 만드는 방향**을 먼저 검토한다. 종종 데이터 특성이 후자를 허용한다.
- **쓰기 코드는 쓰기 일만**. 캐시는 읽기 쪽의 관심사다. 쓰기가 캐시 키를 알고 있으면 두 코드가 서로의 사정에 묶인다.
- TTL 길이는 **"동일 키의 평균 재조회 간격"보다 약간 길게.** 재조회가 짧게 몰리면 캐시가 작동하고, 그 뒤는 신선한 값.
- 옛 값이 보이면 안 되는 데이터는 **아웃박스로 보장**한다. 그 비용을 치를 가치가 있는 데이터인지는 **"옛 값이 보이는 비용"과 "무효화를 보장하는 비용"**을 비교해 정한다.
