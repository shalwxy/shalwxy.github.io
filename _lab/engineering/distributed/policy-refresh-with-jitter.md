## 문제

각 서비스 인스턴스는 **정책**(호출 제한 규칙, 차단 목록 등)을 정책 서비스에서 주기적으로 다시 읽는다. 주기는 60초. 인스턴스가 수십 개다.

정책 서비스의 모니터링을 보니 **60초마다 요청이 뾰족하게 치솟았다.** 평소엔 거의 0이다가 특정 초에 수십 건이 한꺼번에 들어오고, 그 순간 DB 커넥션 풀과 응답 지연이 함께 튄다. 정책 서비스 자체는 트래픽이 적은 서비스라 이 **주기적 스파이크**가 가장 큰 부하였다.

원인은 단순했다. 모든 인스턴스가 **같은 배포로 거의 동시에 시작**하고, 같은 60초 주기로 돌기 때문에 **박자가 맞아 버린다.** 시작 시각이 몇 초 어긋나도 주기가 같으면 그 어긋남이 영원히 유지될 뿐 흩어지지 않는다.

## 시도 1 — 고정 주기 ticker

### 접근

Go의 `time.Ticker`로 60초마다 refresh.

```go
ticker := time.NewTicker(60 * time.Second)
defer ticker.Stop()
for {
    select {
    case <-ticker.C:
        refreshPolicies(ctx)
    case <-ctx.Done():
        return
    }
}
```

### 결과

**실패** — 위에서 본 스파이크 그대로다.

### 분석

ticker는 **정확히 같은 간격**으로 tick을 낸다. 인스턴스 A가 10:00:00에, B가 10:00:02에 시작했다면 둘은 영원히 2초 차이로 돈다. 배포가 롤링으로 이루어져도 인스턴스 시작 시각은 몇 초 안에 몰리고, 그 몰림이 **주기마다 그대로 재현**된다.

분산이 되려면 **간격 자체가 인스턴스마다, 회차마다 달라야** 한다.

## 시도 2 — timer에 무작위 간격 (jitter)

### 접근

`time.Timer`를 쓰고, 매 회차 다음 간격을 **60초 ± 최대 5초**로 무작위로 정한다.

```go
func nextInterval() time.Duration {
    jitter := time.Duration(rand.Int63n(int64(10*time.Second))) - 5*time.Second   // -5s ~ +5s
    return 60*time.Second + jitter
}

timer := time.NewTimer(nextInterval())
defer timer.Stop()
for {
    select {
    case <-timer.C:
        refreshPolicies(ctx)
        timer.Reset(nextInterval())   // 매 회차 다른 간격
    case <-ctx.Done():
        return
    }
}
```

### 결과

**성공** — 스파이크가 사라졌다. 첫 회차에서 ±5초 안에 흩어지고, 회차가 거듭될수록 인스턴스들의 위상이 **랜덤 워크**(매 회차 무작위로 흔들리는 움직임)처럼 계속 벌어져 60초 전체에 고르게 퍼진다.

### 분석

jitter의 핵심은 **"매 회차"** 무작위라는 점이다. 시작 시각만 한 번 흩뿌리면(예: 시작 시 `rand` 만큼 sleep) 그 뒤로는 다시 고정 주기가 되어 위상이 굳는다. 매 회차 간격이 달라야 위상이 계속 섞인다.

±5초는 주기(60초)의 약 8%다. 너무 작으면 흩어지는 데 오래 걸리고, 너무 크면 "정책이 최대 얼마나 늦게 반영되는가"의 상한이 커진다. 주기의 5~15% 정도가 보통 쓰인다.

다만 `time.Timer`는 `Reset` 규칙이 까다롭다. 분산 폭을 좁혀도 되는 규모라면, 같은 효과를 더 단순한 코드로 얻을 수 있다.

## 시도 3 — ticker + tick 뒤 무작위 지연 (채택)

### 접근

실제 작업에서는 같은 날 `Ticker → Timer(jitter) → 다시 Ticker` 순서로 두 번 고쳤다. 마지막 형태는 **고정 주기 ticker를 유지하되, tick을 받은 뒤 refresh 전에 0~5초 무작위로 기다리는** 것이다.

```go
ticker := time.NewTicker(60 * time.Second)
for {
    select {
    case <-ticker.C:
        time.Sleep(time.Duration(rand.Int63n(int64(5 * time.Second))))   // jitter
        refreshPolicies(ctx)
    case <-ctx.Done():
        return
    }
}
```

### 결과

**성공** — 스파이크가 사라지는 건 시도 2와 같고, `timer.Reset`을 쓰지 않아 그 함정이 없다. 분산은 매 회차 0~5초 안에서만 일어나 시도 2보다 좁지만, 인스턴스가 수십 개면 그걸로 충분했다.

### 분석

| | timer + Reset | ticker + 지연 |
|---|---|---|
| 위상 분산 | 회차마다 누적 (넓게 퍼짐) | 매 회차 0~5초 안에서만 (좁게 퍼짐) |
| 코드 | `Reset` 호출을 빠뜨리면 멈춤. 채널 drain 규칙이 까다로움 | ticker가 알아서 다음 tick을 냄 |
| 주기의 정확성 | 평균 60초, 편차 누적 | 정확히 60초 + 0~5초 |

인스턴스가 수십 개 수준이면 **좁게 퍼져도 충분**했다. 거기에 `timer.Reset`의 함정(stop 후 채널을 비우지 않으면 유령 tick, Reset을 잊으면 영원히 멈춤)을 피하는 쪽이 유지보수에 유리해 ticker + 지연으로 확정했다. 인스턴스가 수백 개라 60초 전체에 고르게 퍼져야 한다면 timer 쪽이 맞다.

## 다른 방법 — 서버가 밀어 주기 (push)

갱신 주기를 클라이언트가 정하지 않고, **정책이 바뀔 때만 정책 서비스가 알려 주는** 구조도 있다.

- Kafka 토픽에 "정책 변경" 이벤트를 발행하고 각 인스턴스가 구독
- 또는 gRPC server-streaming으로 연결을 유지하며 변경을 수신

- 얻는 것: 주기적 polling 자체가 없어 스파이크도 없고, **변경이 즉시 반영**된다.
- 치르는 것: 연결·구독 상태를 관리해야 하고, 이벤트를 놓쳤을 때(재시작 중 발행 등)를 대비해 **결국 주기적 polling을 안전망으로** 같이 둬야 한다.
- 변경 반영 지연이 **수 초 안이어야** 하거나, 인스턴스가 수백 개라 polling 자체가 부담일 때 고른다. 60초 지연이 허용되고 인스턴스가 수십 개면 jitter polling이 훨씬 단순하다.

## 정리

| 방식 | 분산 | 코드 복잡도 | 적합한 자리 |
|---|---|---|---|
| 고정 ticker | 안 됨 | 가장 단순 | 인스턴스 1~2개 |
| timer + 회차마다 무작위 간격 | 넓게 | `Reset` 규칙 주의 | 인스턴스 수백 개 |
| **ticker + tick 뒤 무작위 지연 (채택)** | 좁게 | 단순 | 인스턴스 수십 개 |
| 다른 방법. push | polling 없음 | 연결 관리 + polling 안전망 | 즉시 반영이 필요할 때 |

**채택: 시도 3.** 같은 주기로 도는 인스턴스는 **시작 시각이 어긋나도 위상이 굳는다.** 간격이나 실행 시점에 **매 회차** 무작위를 섞어야 흩어진다.

- 주기적 polling이 여러 인스턴스에서 돈다면 **jitter를 기본으로** 넣는다. 스파이크가 보인 뒤에 넣으면 이미 장애다.
- jitter는 **매 회차** 적용한다. 시작 시 한 번만 흩뿌리면 그 뒤로 다시 박자가 맞는다.
- jitter 폭은 **주기의 5~15%**. 폭이 곧 "정책 반영이 최대 얼마나 늦어지나"의 상한이다.
- `timer.Reset`은 함정이 많다. 분산 폭이 좁아도 되면 **ticker + 지연**이 유지보수에 낫다.
