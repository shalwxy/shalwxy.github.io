## 문제

웹 서비스에 **실시간 알림**을 붙여야 했다. 사용자가 웹을 열고 있는 동안 서버가 "거래 체결됐어요", "KYC 승인됐어요" 같은 알림을 밀어 넣는다.

전송 방식으로 **SSE(Server-Sent Events)**를 골랐다 — 서버 → 클라이언트 단방향 푸시가 필요했고, WebSocket의 양방향·바이너리 기능까지는 필요 없었다. SSE는 HTTP 위에서 돌아 방화벽·프록시 통과가 자연스럽고, 브라우저 `EventSource` API가 재연결까지 자동으로 해 준다.

서비스가 처음 올라간 뒤 **세 가지를 바꿨다.** 각각은 알림 서비스의 "역할 경계"를 좁히는 결정이었다. 하나씩 정리한다.

## 결정 1 — "모든 사용자에게 알림" 기능 제거

### 상황

초기 스펙에는 **전체 사용자 공지** 기능이 있었다. "점검 안내", "이벤트 공지"처럼 운영자가 백오피스에서 한 번 쓰면 모든 활성 사용자에게 밀어 넣는다.

### 문제

운영에서 돌려 보니 **알림 서비스가 이 기능을 감당하지 못했다.** 동시 접속 사용자가 수만 명이면 한 번의 "전체 공지"가 알림 서비스에 **수만 개의 SSE 이벤트 fan-out**을 요구한다.

- **메모리 폭증** — 보낼 메시지가 각 연결의 송신 버퍼에 쌓인다
- **DB·캐시 쿼리 폭증** — 사용자별 필터링·개인화를 거치는 경우 사용자 수만큼 조회
- **느린 연결 하나가 뒤 전부를 막음** — 순차 처리면 뒷사람이 못 받고, 병렬 처리면 리소스가 폭발

실제로 전체 공지를 한 번 쏘면 몇 분 동안 알림 서비스가 **다른 요청(개별 알림)을 못 처리**했다. 더 나쁜 건, 전체 공지가 **하루에 몇 번 안 쓰는 기능**이라는 점이었다. 평상시 쓰지도 않는 기능이 서비스를 죽인다.

### 결정 — 기능 자체를 없앴다

기획팀과 이야기해 **전체 공지 기능을 제거**했다. 운영 공지는 다른 수단(이메일·웹사이트 상단 배너·외부 공지 페이지)으로 넘겼다.

### 분석 — "기능을 안 만드는" 선택

성능 문제가 생기면 대부분 **구현을 더 잘 하는 쪽**을 먼저 생각한다 — 큐·워커·샤딩·백프레셔. 그런데 이 기능의 경우 **하루 사용 빈도가 극히 낮고, 다른 수단으로 충분히 대체 가능**했다. 투자 대비 효과가 안 맞았다.

알림 서비스의 설계 중심을 **"개별 사용자에게 정확히 전달"**로 잡으면, 전체 공지는 완전히 다른 축의 기능이다. 하나의 서비스가 두 축을 다 맡으면 둘 다 나빠진다 — 개별 전송이 전체 공지의 자원 요구에 끌려다닌다.

**"만들 수 있다"와 "만들어야 한다"는 다르다.** 기능 요구를 받으면 "어떻게 만들까" 전에 "**정말 필요한가, 다른 수단은 없나**"를 먼저 묻는 습관이 생겼다.

## 결정 2 — 알림의 제목·본문·URL을 백엔드에서 조립

### 상황

알림의 각 요소는 이렇게 생겼다.

```json
{
  "id": "abc-123",
  "type": "credit_card_verification_failed",
  "payload": { "card_last4": "1234", "reason": "unsupported_card_type" },
  "created_at": "2025-08-20T10:00:00Z"
}
```

처음엔 **프론트가 `type`과 `payload`를 보고 제목·본문·링크를 조립**했다. 알림이 쓰이는 자리마다(웹 알림 드롭다운, 이메일, 푸시, 백오피스 뷰어) **같은 조립 코드를 중복** 작성했다.

### 문제

- **알림 종류가 추가될 때마다** 웹·이메일·푸시·백오피스 네 자리를 동기화해야 했다. 한 자리를 빠뜨리면 그 채널에서만 "제목 없음"으로 뜬다.
- **알림 문구는 운영이 자주 바꾸는** 영역이다. "결제 실패" → "카드 등록에 실패했어요" 같은 문구 변경이 프론트 배포를 거쳐야 했다.
- **URL 생성이 프론트 라우팅 지식**에 의존했다 — "KYC 재인증 알림을 클릭하면 어디로 보낼까?"를 프론트가 결정한다. 라우트가 바뀌면 모든 알림 조립 코드가 깨진다.

### 결정 — 서버가 미리 조립해서 내려 준다

알림 생성 시점에 **제목·본문·URL을 미리 조립해 저장**한다. 응답에는 이 값들을 그대로 포함한다.

```json
{
  "id": "abc-123",
  "type": "credit_card_verification_failed",
  "title": "카드 등록에 실패했어요",
  "message": "지원하지 않는 카드 종류입니다. 다른 카드로 다시 시도해 주세요.",
  "link_url": "/account/payment-methods",
  "link_new_window": false,
  "payload": { "card_last4": "1234", "reason": "unsupported_card_type" },
  "created_at": "2025-08-20T10:00:00Z"
}
```

프론트는 **"받은 문자열을 그대로 표시"**만 한다. URL은 받은 그대로 `<a href>`에 넣는다.

### 분석 — 알림 문구의 "진실의 원천"을 하나로

이 결정은 **"같은 데이터를 두 자리 이상에서 조립하지 않는다"**는 원칙의 적용이다.

| 접근 | 조립 자리 | 변경 비용 |
|---|---|---|
| 프론트 조립 | 웹·이메일·푸시·백오피스 각자 | N곳 수정, 배포 N번 |
| **서버 조립 (채택)** | 알림 서비스 한 곳 | 1곳 수정, 배포 1번 |

중요한 부수 효과 하나 — **알림 문구의 원문이 DB에 저장**된다. 사용자가 "그때 받은 알림이 뭐였나요"를 물으면 그 시점 그 문구 그대로 재현할 수 있다. 프론트 조립은 "지금의 조립 코드가 과거 payload를 어떻게 해석하냐"에 달려 있어 재현이 불안정하다.

### 비용

- 알림 서비스가 **각 알림 종류의 payload 구조를 알아야** 한다. 새 종류가 추가되면 알림 서비스 쪽에 조립 코드를 더해야 한다 — 프론트 중복보다 훨씬 집중된 작업이지만, "알림 서비스가 모든 도메인을 알아야 한다"는 결합은 생긴다.
- **다국어 지원**을 넣을 때 조립 책임도 함께 확장된다. 서버가 locale별로 문구를 조립하거나, 조립을 미루고 `title_key`만 저장해 프론트가 locale 파일에서 치환하는 식.

## 결정 3 — JWT 검증을 알림 서비스가 직접

### 상황

SSE 연결은 긴 커넥션이다. 사용자가 로그인한 뒤 수십 분·수 시간 동안 연결을 유지한다. 처음 연결 맺을 때 **JWT를 검증**해 사용자를 식별해야 한다.

초기 구조는 "**계정 서비스에 토큰 검증을 위임**"이었다 — 알림 서비스가 SSE 연결 요청을 받으면 계정 서비스에 `VerifyToken` RPC를 호출해 결과를 받는다.

```
클라이언트 ──(토큰 포함 SSE 연결)──> 알림 서비스
                                      ↓ VerifyToken RPC
                                   계정 서비스
                                      ↓
                                   유효한지 응답
```

### 문제

- **연결마다 계정 서비스 호출**이 발생. 동시 접속이 많아지면 계정 서비스 부하가 늘어난다.
- **알림 서비스가 계정 서비스 장애에 묶임** — 계정 서비스가 다운되면 알림 연결 자체를 못 맺는다. 이미 맺은 연결도 토큰이 만료되면 재검증을 위해 또 호출한다.
- **네트워크 지연**이 연결 수립 시간에 더해진다.

### 결정 — 알림 서비스가 JWT 검증을 직접

JWT는 **자체 검증 가능한 토큰**이다(서명과 만료 시간이 토큰 안에 들어 있고, 공개 키만 있으면 서명을 검증할 수 있다). 외부 서비스를 호출할 필요가 애초에 없다. 알림 서비스에 공개 키를 주입해 **로컬에서 서명 검증**한다.

```go
func (s *NotificationService) authenticate(r *http.Request) (*User, error) {
    tokenString := extractBearerToken(r)
    claims := &UserClaims{}
    _, err := jwt.ParseWithClaims(tokenString, claims, func(t *jwt.Token) (any, error) {
        return s.publicKey, nil   // 로컬 검증
    })
    if err != nil {
        return nil, err
    }
    return &User{ID: claims.Subject}, nil
}
```

### 분석 — JWT의 설계 전제를 쓴다

JWT의 핵심 설계는 **"자체 검증(stateless)"**이다. 토큰이 발급자의 비밀키로 서명돼 있고, 수신자는 공개키로 검증한다. "발급자에게 매번 물어보지 않아도 된다"가 장점이다.

그런데 이 장점을 쓰려면 **각 서비스가 공개키와 검증 로직을 가져야** 한다. 이게 공유 라이브러리로 제공되면 서비스 하나하나가 검증을 자체적으로 할 수 있다. 처음부터 그렇게 설계됐어야 했는데, 초기에 "계정 서비스에 위임"으로 짰던 것은 JWT의 설계와 맞지 않는 선택이었다.

| 접근 | 확장성 | 장애 전파 | 호출당 지연 |
|---|---|---|---|
| 계정 서비스 위임 | 계정 서비스가 병목 | 계정 서비스 다운 → 알림 다운 | +RPC 왕복 |
| **로컬 검증 (채택)** | 각 서비스가 독립 | 없음 | 미미 (마이크로초 단위) |

### 대신 확인해야 할 두 가지

- **공개키 배포** — 모든 서비스가 같은 공개키를 가져야 하고, 키 교체(rotation) 때 동시에 바꿔야 한다. 설정 서비스나 시크릿 매니저에서 같은 키를 받아 쓰도록 한다.
- **토큰 폐기** — JWT는 만료 전에 "무효화"하기 어렵다(발급자에 묻지 않으니까). 사용자가 로그아웃하거나 토큰이 탈취된 경우를 처리하려면 **짧은 만료 시간 + 리프레시 토큰** 또는 **폐기 목록(revocation list)**을 둔다. 서비스가 다루는 데이터의 민감도에 따라 둘 중 하나를 고른다.

## 정리 — 세 결정의 공통점

세 결정은 각기 다른 문제를 다뤘지만 바닥에 같은 생각이 깔려 있다.

| 결정 | 뺀 것 | 얻은 것 |
|---|---|---|
| 1. 전체 공지 기능 제거 | 저빈도 고부하 기능 | 서비스가 **"개별 전송"이라는 한 축**에 집중 |
| 2. 서버에서 문구 조립 | 네 자리의 중복 조립 | 알림 문구의 **"진실의 원천"이 하나** |
| 3. JWT 로컬 검증 | 계정 서비스 왕복 | 알림 서비스가 **계정 서비스 장애에서 독립** |

- 서비스의 **역할 경계**를 좁게 잡는다. "이것도 할 수 있어"가 아니라 "이건 다른 수단에 맡겨도 된다"를 먼저 본다.
- 같은 데이터·결정을 여러 자리에서 조립하고 있으면, 그중 한 자리에 **진실의 원천**을 두고 나머지는 그 결과를 소비한다. 변경 비용이 몇 배 줄어든다.
- 외부 서비스에 매번 묻는 호출을 발견하면, 그 **호출이 정말 필요한지** 다시 본다. JWT처럼 자체 검증 가능한 데이터, 자주 안 바뀌는 설정은 로컬에서 처리할 수 있다.
- SSE는 **긴 연결이라 초기 비용이 모든 사용자 수만큼 곱해진다.** 연결 수립 시점에 걸리는 외부 호출은 가능한 한 다 제거한다.
