## 문제

거래 이벤트를 받아 테이블에 적재하는 컨슈머가 있다. 같은 거래가 **같은 이벤트로 두 번 도착하는 일**이 생각보다 자주 일어난다.

- 생산자가 at-least-once로 발행한다 (한 번만 보장이 아니라 "적어도 한 번")
- 컨슈머가 처리 중 재시작해 오프셋을 다시 읽는다
- 브로커·네트워크의 일시 장애로 재전송된다

결과는 테이블에 같은 거래가 여러 행으로 들어온다. 조회할 때마다 중복이 보이고, 사용자가 카드에 "똑같은 거래"가 두 번 찍힌다고 문의한다.

해결 방향은 하나다 — **같은 거래는 저장이 한 번만 되어야 한다.** 문제는 "같은 거래"를 **무엇으로 판별할 것인가**다.

## 시도 1 — 애플리케이션에서 확인 후 삽입

### 접근

컨슈머가 삽입 전에 기존 행을 조회한다.

```go
func (h *Handler) Handle(ctx context.Context, evt Event) error {
    existing, err := repo.FindBy(ctx, evt.Timestamp, evt.FromAddr, evt.ToAddr, evt.Amount)
    if err != nil { return err }
    if existing != nil {
        return nil   // 이미 있음, 건너뜀
    }
    return repo.Insert(ctx, evt)
}
```

"같은 건"을 판별하기 위해 **의미 있어 보이는 컬럼 몇 개의 복합 키**(시간 + 보낸이 + 받는이 + 금액)를 쓴다.

### 결과

**실패** — 두 가지 이유로 깨진다.

1. **복합 키가 "같은 건"을 정확히 집지 못한다.** 같은 보낸이가 같은 받는이에게 같은 금액을 짧은 간격으로 두 번 보내는 정상 거래가 있으면, 복합 키는 둘을 같은 건으로 본다.
2. **조회와 삽입 사이에 틈이 있다.** 이전 글의 [TOCTOU](/lab/engineering/distributed/preempt-over-check/)와 같은 문제다. 두 컨슈머 인스턴스가 같은 이벤트를 동시에 받으면, 둘 다 "없다"고 조회한 뒤 둘 다 삽입한다.

### 분석

이 코드가 암묵적으로 전제하는 것은 **"같은 거래를 유일하게 가리키는 자연 키가 있다"**는 것이다. 그런데 시간·금액·주소 조합은 **같은 건을 집는 키가 아니라 비슷한 건을 집는 쿼리**다. 자연 키를 잘못 고른 상태에서는 어떤 방법을 써도 정확할 수 없다.

## 시도 2 — 식별자를 찾아 복합 키에 포함

### 접근

플랫폼이 거래마다 부여하는 **고유 식별자**(여기선 트랜잭션 해시)를 컬럼으로 추가해 복합 키에 넣는다.

```sql
CREATE UNIQUE INDEX idx_activity_identity
  ON activities (event_type, tx_hash, from_address);
```

### 결과

**부분 성공** — 자연 키가 정확해져 같은 거래는 같은 키를 갖는다. 그런데 **일부 이벤트 종류에서 또 중복이 났다.**

원인은 **거래 종류마다 "안정적인 식별자"가 다르다**는 데 있었다. 예:

- 일반 전송·민트: `tx_hash`가 거래당 하나라 잘 동작한다.
- **소모성 아이템 거래**(여러 건을 묶어 한 트랜잭션으로 처리): 플랫폼은 **판매자 쪽 주문 해시**를 기본 식별자로 돌려주는데, 같은 판매 글에서 여러 건이 팔리면 **판매자 주문 해시가 반복**된다. 반면 구매자 주문 해시는 구매 건별로 유일하다.

### 분석

"플랫폼이 주는 식별자"가 늘 유일한 것은 아니다. **거래 모델이 1:1이 아니라 1:N**이면, 플랫폼이 "거래의 한쪽"에 식별자를 두느냐 "다른 쪽"에 두느냐에 따라 유일성이 달라진다. 복합 키를 짤 때 **"이 컬럼이 이벤트 종류마다 정말 유일한가"**를 종류별로 확인해야 한다.

## 시도 3 — 종류에 맞는 유일 컬럼을 고르고 유니크 제약으로 (채택)

### 접근

소모성 아이템 이벤트에서는 **구매자 주문 해시**를 저장하도록 바꾸고, DB에 **유니크 인덱스**를 건다. 애플리케이션의 선조회는 제거한다.

```sql
CREATE UNIQUE INDEX idx_activity_identity
  ON activities (event_type, tx_hash, identity_hash);
-- identity_hash = 일반 거래의 자기 해시, 소모성 아이템의 구매자 주문 해시 등
```

```go
func (h *Handler) Handle(ctx context.Context, evt Event) error {
    err := repo.Insert(ctx, evt)
    if isUniqueViolation(err) {
        return nil   // 중복 = 이미 있음, 성공으로 처리
    }
    return err
}
```

### 결과

**성공** — 중복 삽입이 사라지고, 코드가 짧아졌다. 두 컨슈머가 같은 이벤트를 동시에 받아도 DB가 둘 중 하나만 받고 다른 쪽에 중복 키 오류를 돌려준다. 컨슈머는 그 오류를 "이미 있음"으로 해석해 **삽입 성공과 같은 응답**을 돌려준다.

### 분석 — 왜 애플리케이션 조회가 아니라 DB 제약인가

같은 중복을 두 자리에서 막을 수 있다. 결과는 같아 보이지만 보장의 질이 다르다.

| | 애플리케이션 선조회 | DB 유니크 제약 |
|---|---|---|
| 동시성 | 조회·삽입 사이에 틈이 있음 (TOCTOU) | 틈 없음 — DB가 원자적으로 판정 |
| 성능 | 삽입마다 조회 한 번 추가 | 유니크 인덱스에 삽입 시 한 번만 검사 |
| 코드량 | 조회 + 비교 + 삽입 | 삽입 + 에러 분기 |
| 안전망 | 애플리케이션 버그·실수에 취약 | **다른 경로(배치, 수동 INSERT)에도 유효** |

마지막 줄이 가장 중요하다. 컨슈머에만 중복 체크를 두면 **그 컨슈머를 거치지 않는 모든 경로**(수동 데이터 패치, 백오피스에서의 삽입, 다른 서비스가 같은 테이블을 쓰는 경우)가 보호되지 않는다. 유니크 제약은 **테이블을 쓰는 모든 경로에 자동으로 적용**된다.

### "이미 있음"을 성공으로 처리하기

유니크 위반 에러를 **에러로 올리면 컨슈머가 재시도를 반복**한다. 두 번째·세 번째 시도도 같은 이유로 실패하면 결국 DLQ로 간다 — "중복이라 저장을 못 한" 것인데 "실패"로 분류된다.

올바른 처리는 "이미 있음"을 **삽입 성공과 같게** 처리하는 것이다. 멱등 처리의 핵심 패턴이다 — **"요청을 두 번 받아도 결과가 같다"**를 상태 전이에 맞게 번역하면, 중복 삽입 시도는 "이미 원하는 상태"를 뜻하므로 성공이다.

```go
if isUniqueViolation(err) {
    return nil   // 성공으로 처리, 재시도·DLQ로 넘기지 않음
}
```

## 다른 방법 — 유니크 키가 없을 때의 대안들

위 패턴이 성립하려면 **"같은 건"을 가리키는 안정된 식별자**가 있어야 한다. 그렇지 않은 경우가 둘 있었다.

**크로스체인 거래**의 경우, 거래의 한쪽 체인에서 받은 식별자가 **다른 체인으로 가는 동안 바뀐다.** 처음엔 출발 체인의 해시를, 도착해서 결과가 오면 도착 체인의 해시를 받는데, 둘이 다른 값이다. 이땐 유니크 키를 포기하고 **별도의 "연결용 키"**(출발 해시와 도착 해시를 묶는 ID)를 플랫폼이 공급하도록 맞췄다. 유니크 제약은 그 연결용 키에 건다.

**순서가 보장되지 않는 메시지**(나중에 들어온 메시지가 더 앞선 상태를 담고 있는 경우) — 삽입이 아니라 **UPSERT + 조건부 UPDATE**가 필요하다. "이 메시지의 타임스탬프가 현재 저장된 것보다 크면 갱신"처럼 `WHERE updated_at < $1`을 붙여 늦게 도착한 오래된 메시지를 거른다.

```sql
INSERT INTO activities (identity_hash, ...)
VALUES ($1, ...)
ON CONFLICT (identity_hash) DO UPDATE
   SET status = EXCLUDED.status, updated_at = EXCLUDED.updated_at
 WHERE activities.updated_at < EXCLUDED.updated_at;
```

## 정리

| 방식 | 중복을 막는 자리 | 적합한 자리 |
|---|---|---|
| 애플리케이션 선조회 | 컨슈머 코드 안 | 식별자가 없거나 유니크 제약을 걸 수 없을 때 (약한 보장) |
| **DB 유니크 제약 (채택)** | 테이블 레벨 | 안정적인 식별자가 있고, 테이블을 여러 경로가 쓸 때 |
| 다른 방법. UPSERT + 조건부 UPDATE | 테이블 레벨 | 삽입이 아니라 상태 갱신이고, 메시지 순서가 보장되지 않을 때 |

**채택: DB 유니크 제약.** 중복을 막는 가장 간단한 방법은 DB에 맡기는 것이다. 그러려면 "같은 건"을 가리키는 **안정된 식별자**를 먼저 확정해야 하고, 거래 종류마다 그 식별자가 다를 수 있다는 점을 염두에 둔다.

- "확인하고 없으면 삽입"을 발견하면 **유니크 제약**으로 바꿀 수 있는지 먼저 본다. 가능하면 애플리케이션 코드가 줄고 다른 경로까지 보호된다.
- "같은 건"의 정의는 **거래 모델이 1:1인가 1:N인가**에 따라 달라진다. 플랫폼이 주는 식별자가 종류마다 유일한지 종류별로 확인한다.
- **유니크 위반은 "이미 있음"으로 번역해 성공 처리**한다. 그래야 재시도·DLQ 경로가 자연스럽게 동작한다.
- 식별자가 중간에 바뀌는 도메인(크로스체인·다단계 처리)은 **별도의 연결용 키**를 플랫폼이 공급하게 하거나, UPSERT + 조건부 UPDATE로 넘어간다.
