## 문제

Kafka로 들어오는 이벤트를 받아 테이블에 적재하는 컨슈머가 있다. 이벤트는 대부분 정상이지만 가끔 **비정상**이다 — 필드가 비어 있거나, 외래 키가 없는 ID를 참조하거나, 생산자의 버그로 스키마가 깨져 있다.

이 "이상한 메시지"를 어떻게 처리할 것인가. 선택지는 두 축이다.

| 축 | 선택지 |
|---|---|
| **저장** | DB에 저장 vs 저장 안 함 |
| **실패 처리** | 컨슈머가 `error`를 반환해 재시도/DLQ 경로를 타게 할지 vs 삼키고 다음 메시지로 넘어갈지 |

애초에 "비정상이지만 저장은 하는" 선택은 자연스러워 보인다. **데이터를 잃고 싶지 않다**는 본능이 있고, 혹시 나중에 보정해야 할지도 모른다. 하지만 이 선택이 DB를 넘어 코드와 운영에 어떤 비용을 만들었는지, 세 번의 시도를 거치며 보게 됐다.

## 시도 1 — 저장은 하고 조회에서 숨기기

### 접근

테이블에 `is_valid BOOLEAN` 컬럼을 추가하고, 비정상 메시지도 전부 저장한다. 다만 사용자에게 보이는 조회 경로에서는 `WHERE is_valid = true`로 걸러 낸다.

```go
func (h *Handler) Handle(ctx context.Context, msg *Message) error {
    evt, err := parse(msg.Payload)
    isValid := err == nil && evt.TokenID != "" && evt.OwnerAddress != ""
    return repo.Insert(ctx, Activity{
        ...evt,
        IsValid: isValid,
    })
}
```

```sql
SELECT * FROM activities
WHERE wallet_address = $1
  AND is_valid = true    -- ← 비정상 숨기기
ORDER BY created_at DESC
LIMIT 20;
```

### 결과

**부분 성공** — 사용자 쪽에서는 비정상이 안 보이고, 운영자는 `WHERE is_valid = false`로 들여다볼 수 있다. "데이터는 다 가지고 있다"는 안도감이 있다.

### 분석

운영해 보니 세 가지 비용이 조용히 쌓였다.

1. **모든 조회에 `is_valid = true`가 따라붙는다.** 목록 조회, 카운트, 집계, 통계 — 비정상 데이터가 끼면 안 되는 모든 쿼리에 조건이 들어간다. 빠뜨리면 숫자가 이상해지고, 어느 쿼리가 빠뜨렸는지 찾기 어렵다.
2. **인덱스가 복잡해진다.** `(wallet_address, created_at)` 하나면 충분했던 인덱스가 `(wallet_address, is_valid, created_at)`이 되거나, `WHERE is_valid = true` 조건부 인덱스를 따로 두게 된다. 테이블의 비정상 비율이 낮다면 인덱스 비용이 그만큼 낭비다.
3. **"비정상인 활동"이라는 개념이 도메인에 섞인다.** 비즈니스 모델엔 없는 상태인데 ORM·DTO·GraphQL 스키마에까지 `is_valid`가 번진다.

세 가지 다 "숨기면 보이지 않는다"는 전제에 기대고 있었다. 그런데 **숨기는 조건을 모든 자리에 빠짐없이 걸어야** 그 전제가 유지되고, 그걸 사람이 매번 지켜야 한다.

## 시도 2 — 조건절을 지우고 "가끔 보이게 두기"

### 접근

인덱스와 가독성이 거슬려 조건절을 지웠다. 비정상 데이터는 여전히 DB에 있지만, 조회 결과에 가끔 섞여 나오는 것은 **"원래 적다"**는 가정으로 받아들였다.

```sql
SELECT * FROM activities
WHERE wallet_address = $1
ORDER BY created_at DESC
LIMIT 20;    -- is_valid 조건 제거
```

### 결과

**실패** — 비정상이 몇 건이라도 사용자 화면에 노출되면 CS가 들어온다. "제 지갑에 이상한 거래가 뜹니다." 비율이 낮든 높든 **보이면 안 되는 것은 보이면 안 된다.**

### 분석

"숨기는 비용"과 "숨기지 않는 비용" 중 어느 쪽도 공짜가 아니었다. 조건절을 치면 인덱스·가독성이 나빠지고, 안 치면 가끔 새어 나와 신뢰가 깎인다. 양쪽 다 **"비정상을 DB에 넣기 때문에"** 생긴 비용이다. 문제 정의를 되돌아보니 **DB에 안 넣는 쪽**이 아직 남아 있었다.

## 시도 3 — 저장하지 않고 DLQ로 (채택)

### 접근

컨슈머가 비정상을 판정하면 `error`를 반환한다. 메시지 미들웨어가 재시도 정책에 따라 몇 번 더 시도한 뒤 **DLQ(Dead Letter Queue)** 토픽으로 보낸다. DB에는 처음부터 아무것도 쓰지 않는다.

```go
func (h *Handler) Handle(ctx context.Context, msg *Message) error {
    evt, err := parse(msg.Payload)
    if err != nil {
        return errors.Wrap(err, "unmarshal event")   // 재시도 → DLQ
    }
    if evt.TokenID == "" || evt.OwnerAddress == "" {
        return errors.New("invalid event: required field missing")  // 재시도 → DLQ
    }
    return repo.Insert(ctx, toActivity(evt))
}
```

애플리케이션은 짧은 재시도 후 포기하고, 메시지 브로커 쪽 설정이 **DLQ 토픽**과 **재시도 지연**(예: 24분)을 맡는다.

```yaml
consumer:
  topic: activity.asset-result.nft-item
  retry:
    max_attempts: 3
    delay: 24m
  dead_letter_topic: activity.asset-result.nft-item.DLQ
```

### 결과

**성공** — 세 가지 비용이 모두 사라졌다.

- 모든 조회에서 `is_valid` 조건이 빠졌다. 인덱스도 원래대로 되돌렸다.
- 테이블 스키마에서 `is_valid` 컬럼을 지우고 DTO·모델에서도 뺐다. 도메인이 다시 단순해졌다.
- 비정상 메시지는 DLQ 토픽에 쌓인다. 알림이 한 번 울리면 **DLQ 메시지 수만 보면** 지금 얼마나 이상한지 알 수 있다.

### 분석 — DLQ가 DB보다 싼 이유 세 가지

1. **조회 경로가 깨끗해진다.** 비정상을 걸러 내는 조건이 어느 쿼리에도 없다. 쿼리가 늘어나도 자동으로 안전하다 — "빠뜨리면 숫자가 틀어지는" 조건이 애초에 없으니까.
2. **인덱스가 단순해진다.** `is_valid` 같은 운영 전용 컬럼이 인덱스에서 사라진다. 비정상 비율이 낮을수록 이득이 크다.
3. **운영이 한 곳으로 모인다.** "원인을 찾고 재처리할지 결정하는 일"을 DB 쿼리가 아니라 DLQ 토픽 소비자(또는 Kafka UI)에서 한다. 같은 작업을 할 때 도구가 두 개(DB, 모니터링 대시보드)가 아니라 하나다.

### 걱정과 해소

**"그럼 비정상 데이터를 영원히 못 보는 건가?"** DLQ 토픽의 보존 기간(예: 7~30일) 동안 원본 메시지가 그대로 남는다. 필요하면 토픽에서 꺼내 확인하거나 재처리한다. **"원본"**을 보관한다는 점에서 오히려 낫다 — DB에 넣은 것은 이미 `is_valid: false`로 "해석된 후"의 데이터다.

**"재시도가 몰리면 DLQ가 폭주하지 않을까?"** 재시도 지연을 넉넉히 둔다(여기선 24분). 생산자 쪽의 일시 장애면 재시도 안에서 복구되고, 영구적 비정상은 DLQ로 간다. 둘을 **재시도 횟수와 간격**으로 구분한다.

**"DLQ 메시지를 역직렬화할 수 없으면?"** DLQ에 들어간 메시지도 원본 proto 그대로 보존되게 한다. 한 번 "DLQ 메시지에 메타데이터만 보관"으로 바꿨다가 역직렬화가 깨져 원래대로 되돌린 적이 있다 — **DLQ 메시지도 정상 토픽 메시지와 같은 포맷**이어야 재처리 코드를 공유할 수 있다.

## 다른 방법 — 생산자 쪽에서 막기

가장 좋은 비정상은 **아예 발생하지 않은 비정상**이다. 생산자 서비스의 입력 검증·스키마 검증·테스트가 꼼꼼하면 소비자가 받을 비정상은 애초에 줄어든다.

- 얻는 것: DLQ도 재시도도 필요 없다. 생산자가 보장하는 스키마만 믿으면 된다.
- 치르는 것: **내가 소유하지 않는 생산자**(다른 팀의 서비스, 외부 벤더)에 의존한다. 상대가 깨면 내 쪽에서 안전망이 없다.
- 같은 조직 안이라면 **스키마 레지스트리**(Confluent Schema Registry 등)를 써서 생산자·소비자가 같은 스키마로 묶이게 한다. 조직이 다르면 소비자가 DLQ로 받아들이는 쪽이 현실적이다.

## 정리

| 시도 | 핵심 | 결과 |
|---|---|---|
| 1. 저장하고 조회에서 숨김 | `is_valid` 컬럼 + 모든 조회에 조건절 | 조회·인덱스·도메인이 전부 복잡해짐 |
| 2. 조건절 제거 | "비정상은 적으니 가끔 보여도 괜찮다" | 사용자에게 보이면 안 되는 게 보임 |
| **3. DLQ로 보내고 DB엔 안 쓰기 (채택)** | 컨슈머가 `error` 반환 → 재시도 → DLQ | 조회·인덱스·도메인이 모두 깨끗 |
| 다른 방법. 생산자에서 막기 | 스키마 레지스트리·입력 검증 | 생산자를 소유해야 함 |

**채택: 시도 3.** "이상한 데이터도 일단 받아 두자"는 저장 본능은 운영 비용을 조용히 쌓는다. 비정상은 **데이터가 아니라 운영 사건**이고, 운영 사건은 운영 도구(DLQ)에 모으는 쪽이 맞다.

- 메시지 소비자에게 들어오는 비정상을 발견하면, **"저장할지 말지"보다 "이 비정상이 데이터인가 사건인가"를 먼저** 묻는다. 데이터면 DB, 사건이면 DLQ.
- 조회 경로에 `is_valid` 같은 운영 전용 조건절을 걸고 있다면, 그 조건이 **왜 매번 필요한지**를 다시 본다. 필요한 이유가 "저장은 하지만 보이면 안 돼서"라면 저장을 그만두는 쪽이 싸다.
- DLQ 메시지는 **정상 토픽 메시지와 같은 포맷**으로 보존한다. 재처리·분석 코드를 공유할 수 있다.
