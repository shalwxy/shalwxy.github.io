## 문제

게임 캐릭터 민트 흐름에서 **닉네임이 두 번 만들어지는 버그**가 보고됐다. 원인을 좁혀 들어가 보니 코드는 아주 자연스러운 모양이었다.

```go
exists, err := repo.Exists(ctx, nickname)
if err != nil { return err }
if exists {
    return ErrDuplicatedNickname
}
return repo.Create(ctx, nickname, accountID)
```

"있는지 확인하고, 없으면 만든다." 영어로는 **TOCTOU(Time-Of-Check to Time-Of-Use)** 라고 부르는 고전적인 패턴이다. 혼자 돌면 문제가 없지만, 이 함수가 분산 환경에서 **같은 닉네임에 대해 두 번 호출**되면 다음 순서가 가능하다.

```
요청 A: Exists("홍길동") → false
요청 B: Exists("홍길동") → false   ← A가 Create 하기 전
요청 A: Create("홍길동", acc-1)   → OK
요청 B: Create("홍길동", acc-2)   → OK ← 중복 생성
```

핵심은 **확인 시점과 사용(생성) 시점 사이에 틈이 있다**는 것이다. 이 틈에 다른 요청이 끼어들 수 있으면 확인은 아무것도 보장하지 못한다.

## 시도 1 — 확인 범위를 좁히기

### 접근

"한 트랜잭션 안에 Exists와 Create를 묶으면 되지 않을까?" 싶다. 같은 DB 커넥션에서 묶어도 보고, `SELECT … FOR UPDATE`로 행을 잠가도 봤다.

```go
return db.Transaction(ctx, func(tx) error {
    exists, _ := tx.ExistsForUpdate(ctx, nickname)
    if exists { return ErrDuplicatedNickname }
    return tx.Create(ctx, nickname, accountID)
})
```

### 결과

**실패** — `SELECT … FOR UPDATE`는 **존재하지 않는 행을 잠그지 못한다.** 닉네임이 아직 없을 때 두 요청이 동시에 들어오면 둘 다 "없음"을 빈 결과로 받고(잠글 대상이 없으니 서로를 막지 못한다) 둘 다 `Create`로 넘어간다. 행 잠금은 **이미 있는 행**의 동시 수정은 막아도, **"아직 없는 것을 만들려는" 경쟁**은 막지 못한다.

### 분석

"행 잠금"은 **같은 테이블의 이미 존재하는 행**을 두고 경쟁할 때만 유효하다. 그런데 닉네임의 고유성은 사실 `nickname` 테이블 하나의 문제가 아니라 **"이 닉네임에 대해 민트 흐름이 하나만 돌아야 한다"**는 **흐름 단위의 제약**이다. 테이블 밖에 있는 자원(Kafka 메시지의 소비, 캐시, 외부 서비스 호출)까지 묶으려면, 잠금의 축을 **테이블**이 아니라 **흐름의 공통 키**(여기선 닉네임 문자열)로 바꿔야 한다.

## 시도 2 — 유니크 제약으로 "삽입에 맡기기"

### 접근

`nickname` 컬럼에 **유니크 인덱스**를 걸고, 확인 없이 삽입을 시도한다. 중복이면 DB가 에러를 돌려주므로 그걸 "이미 있음"으로 해석한다.

```go
err := repo.Create(ctx, nickname, accountID)
if isUniqueViolation(err) {
    return ErrDuplicatedNickname
}
return err
```

### 결과

**성공** — 두 요청이 동시에 와도 DB가 정확히 한 쪽만 받고 다른 쪽에 중복 키 오류를 돌려준다. 단일 테이블 안의 중복은 이걸로 막힌다.

### 분석

이 방식은 쓸 수 있는 자리에서는 지금도 1순위다. 단일 테이블 안에서는 가장 깔끔하다(뒤의 "다른 방법" 참고). 다만 문제는 민트 흐름이 "닉네임 테이블에 행을 하나 꽂으면 끝"이 아니었다는 점이다. 민트는 블록체인 트랜잭션을 기다리고, 그동안 이벤트 저장소에 중간 상태를 쓰고, 결과에 따라 보상 흐름으로 들어갈 수도 있다. **흐름이 성공할 때까지 닉네임은 다른 요청이 손대지 못하게 "잡아 두고"**, 흐름이 끝나야 비로소 닉네임 테이블에 커밋해야 한다. 유니크 인덱스 삽입은 "커밋 순간"의 중복만 막는다. 그 전까지의 몇 초~몇십 초 동안도 다른 요청을 막으려면 다른 수단이 필요하다.

## 시도 3 — 확인을 없애고 먼저 선점 (채택)

### 접근

확인 자체를 없앴다. 요청이 도착하자마자 **분산 락으로 닉네임 문자열을 선점**하고, 민트 흐름이 끝난 뒤 그 결과에 따라 해제 여부를 결정한다. Redis의 `SETNX`(key가 없을 때만 set)가 이 역할을 한다.

```go
// 흐름 시작: 선점 시도. 이미 누군가 잡고 있으면 AlreadyExists 에러.
lockKey := "preempt:nickname:" + nickname
if err := preempt.Acquire(ctx, lockKey); err != nil {
    if errors.Is(err, preempt.ErrAlreadyPreempted) {
        return ErrDuplicatedNickname
    }
    return err
}

// 민트 흐름 실행 (분/초 단위로 블록체인·이벤트 저장소까지 오가는 긴 작업)
result, err := mintFlow.Run(ctx, nickname, accountID)
if err != nil {
    // 흐름이 실패하면 선점을 풀어서 다른 요청이 재시도할 수 있게 한다
    _ = preempt.Release(ctx, lockKey)
    return err
}

// 흐름이 성공했을 때만 닉네임 테이블에 커밋하고, 선점은 그대로 유지한다
return repo.Create(ctx, nickname, accountID, result)
```

### 결과

**성공** — 두 번째 요청은 `Acquire` 지점에서 바로 `ErrAlreadyPreempted`가 떨어져 흐름 자체에 들어오지 못한다. 선점의 TTL은 민트 흐름의 최대 소요 시간보다 넉넉히 길게 잡는다(흐름이 죽어 선점이 영원히 남는 걸 TTL이 회수한다).

### 분석

- **"확인 → 사용"을 "먼저 잡기 → 사용"으로 뒤집었다.** 분산 락의 Acquire는 "비어 있으면 잡고 성공, 아니면 실패"를 **원자적으로** 처리하므로 그 사이에 끼어들 자리가 없다. 확인과 사용 사이의 틈이 아예 생기지 않는다.
- **락의 키를 "자원 자체의 고유성"**(닉네임 문자열)으로 잡았다. 테이블 행이나 계정 ID가 아니다. 덕분에 "누가 소유하는지"와 무관하게 "이 닉네임에 대한 흐름"을 한 줄로 세울 수 있다.
- 처음에는 선점 해제를 `defer`로 걸어서 "흐름이 끝나면 어떻게든 풀리게" 만들었는데, 이게 **성공한 선점까지 풀어 버렸다.** 그래서 해제 조건을 **흐름 실패 시에만**으로 바꿨다. 성공한 선점은 그대로 둔다 — 닉네임 테이블에 행이 생겼으니, 이후엔 유니크 제약이 받는다. (시도 2의 유니크 인덱스는 그대로 유지한다 — 선점이 TTL로 사라진 뒤의 최종 방어선이다.)

### 해제 시점이 왜 미묘한가

선점은 두 가지 이유로 쓰인다.

| 상황 | 선점의 역할 | 해제 시점 |
|---|---|---|
| 흐름이 실패했다 | 다음 요청이 **재시도**할 수 있게 자원을 되돌려 줘야 함 | **실패 직후** 즉시 해제 |
| 흐름이 성공했다 | 자원이 영구적으로 소유자에게 귀속됨 | **해제하지 않음.** 이후 중복 요청은 유니크 제약으로 걸러진다 |
| 흐름이 시간 초과·크래시 | 선점이 영원히 남지 않아야 함 | **TTL이 회수.** 다음 요청의 Acquire가 자연스럽게 통과한다 |

해제를 `defer`로 두면 두 번째 줄이 깨진다. "성공했으니 아무도 못 쓰게 유지"가 되어야 하는데 끝에서 풀어 버린다. 이 버그는 처음 패치에서 실제로 났고, 해제 호출 자리를 흐름의 **에러 분기 안**으로 옮기는 것으로 고쳤다.

## 다른 방법 — DB 유니크 제약으로 끝내기

흐름이 짧다면(= "한 트랜잭션 안에 삽입만 하면 끝"이라면) 시도 2가 가장 간단하다. Redis·분산 락·TTL 같은 부품이 없어도 되고, DB가 이미 "한 키에 하나만"을 공짜로 제공한다.

```sql
CREATE UNIQUE INDEX idx_nickname ON nicknames (nickname);
```

```go
err := repo.Create(ctx, nickname, accountID)
if isUniqueViolation(err) { return ErrDuplicatedNickname }
return err
```

- 얻는 것: **의존성 0.** Redis 인프라도, 선점 해제 시점에 대한 고민도 없다.
- 치르는 것: 흐름이 "삽입 외에 수십 초 걸리는 외부 호출"을 가지고 있으면, 그 시간 동안 다른 요청이 같은 키로 흐름을 **중복 시작**하는 것을 막지 못한다. 중복 시작 자체가 문제가 아닌 경우(둘 다 똑같이 성공해도 괜찮다)라면 그대로 둬도 되지만, **외부 호출 비용이나 멱등성 문제**가 있으면 선점이 필요하다.
- **흐름이 유니크 삽입 하나로 끝나거나, 흐름의 중복 실행이 비용·부작용을 일으키지 않을 때** 이쪽을 고른다.

## 정리

| 시도 | 핵심 | 결과 |
|---|---|---|
| 1. 행 잠금 | 트랜잭션 + `SELECT … FOR UPDATE` | 아직 없는 행은 못 잠가 중복 생성이 남음 |
| 2. 유니크 인덱스 | DB에 "삽입에 맡기기" | 삽입 순간은 완벽, 흐름 전체는 못 막음 |
| **3. 분산 락 선점 (채택)** | 확인 자체를 없애고 **먼저 잡기 → 사용** | 흐름 전체를 한 줄로 세움 |
| 다른 방법. DB 유니크 제약 | 흐름이 짧으면 삽입에 맡기기 | 의존성 0, 긴 흐름의 중복 시작은 못 막음 |

**채택: 시도 3.** 민트 흐름처럼 "삽입 외에도 외부 호출이 끼어 있는" 긴 흐름에서는 선점이 유일한 선택지다. 흐름이 유니크 삽입 하나로 끝나는 경우라면 유니크 제약이 더 간단하다.

- "있는지 확인하고 없으면 만든다"는 코드를 보면 **TOCTOU**를 의심한다. 확인과 사용 사이에 다른 요청이 끼어들 수 있으면 확인은 아무것도 보장하지 못한다.
- 분산 락의 **키는 흐름의 공통 자원**으로 잡는다. 테이블의 행이나 소유자 ID가 아니라, 경합하는 자원 그 자체(닉네임 문자열, 주문 번호, 트랜잭션 해시 등).
- **선점 해제는 "실패했을 때만".** 성공한 선점은 그대로 둬야 다음 요청이 유니크 제약에 걸린다. `defer`로 풀면 성공까지 풀린다.
- TTL은 흐름의 **최대 소요 시간보다 넉넉히** 둔다. 흐름이 죽어 선점이 영원히 남는 걸 회수하는 안전망이다.
