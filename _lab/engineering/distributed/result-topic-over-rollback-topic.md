## 문제

출금 요청이 들어오면 **"일일 출금 한도"**를 먼저 깎아 두어야 한다. 그 사이에 또 다른 출금 요청이 들어와도 한도를 초과하지 않도록.

```
요청 받음 → 한도 선차감 → 블록체인에 출금 요청 → (몇 분~몇십 분 뒤) → 결과 도착
```

문제는 블록체인 쪽에서 **실패**가 올 수 있다는 점이다. 네트워크 혼잡으로 드랍되거나, 지갑 잔액 부족으로 거절되거나, 사용자가 서명을 안 하거나. 이때 **선차감한 한도를 되돌려야** 한다. 안 되돌리면 사용자가 실제로는 출금하지 못했는데 "오늘 한도 썼음"으로 남는다.

되돌리는 로직 자체는 어렵지 않다 — `daily_withdrawal_used -= amount`. 문제는 **"어떤 신호로 되돌릴까"**다.

## 시도 1 — 롤백 전용 토픽을 따로 두기

### 접근

블록체인 서비스가 출금 실패를 감지하면 **`withdrawal.rollback`** 토픽에 롤백 요청을 발행한다. 한도 서비스는 이 토픽을 구독해 받으면 한도를 되돌린다.

```
블록체인 서비스 → withdrawal.rollback → 한도 서비스 (한도 복구)
```

### 결과

**부분 성공** — 기능적으로는 되돌아간다. 하지만 **같은 데이터 흐름의 토픽이 둘**(결과 토픽, 롤백 토픽)로 늘어나면서 운영이 복잡해졌다.

- **순서 뒤바뀜 가능성이 늘어남** — 결과 토픽과 롤백 토픽이 별개라, 시스템의 어떤 경로에서는 롤백 메시지가 결과 메시지보다 먼저 처리되는 경합이 생겼다.
- **중복 처리 로직을 두 자리에서** — 둘 다 at-least-once라 각각 멱등 처리가 필요하다.
- **"이 출금의 상태가 뭔가"가 흩어짐** — 결과 토픽에 있는 성공·실패와 롤백 토픽에 있는 "되돌림 요청"이 **서로 중복**된다. 성공 이벤트가 결과 토픽에 오면 롤백 이벤트는 나오면 안 되는데, 두 토픽을 통합해서 판단하는 코드가 생긴다.

### 분석

롤백 토픽을 따로 둔 이유는 **"롤백은 특별한 이벤트"**라는 느낌이었다. 보상 로직이라 다른 성공 경로와 분리하는 게 깔끔해 보였다. 그런데 실제로는 **결과 토픽에 이미 "성공/실패"가 다 담겨 있다.** 롤백 토픽은 그중 "실패"를 다시 보내는 것이라, 내용상 중복이다.

Kafka 토픽을 하나 더 두면 **"순서·중복·스키마"**를 하나 더 관리해야 한다. 그 비용이 "분리의 깔끔함"보다 크다.

## 시도 2 — 결과 토픽 하나로, 실패일 때만 되돌리기 (채택)

### 접근

**트랜잭션 결과 토픽**에서 성공·실패·드랍을 모두 받고, **실패일 때만** 선차감을 되돌린다. 성공이면 선차감이 그대로 "확정"이다.

```
블록체인 서비스 → transaction.result → 한도 서비스
                                        ↓
                         result.status == FAILED or DROPPED ?
                                        ↓ yes
                                   한도 복구 (= 선차감 취소)
                                        ↓ no
                                   아무것도 안 함 (= 선차감 확정)
```

```go
func (c *WithdrawalResultConsumer) Handle(ctx, evt ResultEvent) error {
    switch evt.Status {
    case StatusSuccess:
        return nil   // 선차감 그대로 → 확정
    case StatusFailed, StatusDropped, StatusUnknown:
        return c.limitService.Rollback(ctx, evt.WalletAddress, evt.TokenSymbol, evt.Amount)
    default:
        return fmt.Errorf("unexpected status: %v", evt.Status)
    }
}
```

### 결과

**성공** — 구독해야 할 토픽이 하나, 멱등 처리할 자리가 하나, 순서 걱정할 자리가 하나로 줄었다.

### 분석 — "보상은 결과의 한 분기"

선차감 패턴은 **Saga의 보상(Compensation)**에 해당한다. 교과서적인 Saga는 "성공 경로"와 "보상 경로"를 별도로 그리지만, 실무에서는 **"결과가 실패일 때만 보상한다"**는 흐름이 많다. 이때 보상 토픽을 따로 두는 것은 **같은 사건을 두 번 발행**하는 셈이다.

| 구조 | 토픽 수 | 발행자가 알아야 할 것 | 소비자 로직 |
|---|---|---|---|
| 롤백 전용 토픽 | 2 (결과 + 롤백) | "보상이 필요한지 판단해서 롤백 토픽에 넣기" | 두 토픽 각자 처리 + 통합 상태 |
| **결과 토픽 하나 (채택)** | 1 (결과만) | "결과를 그대로 발행" | 결과 상태에 따라 분기 |

발행자가 "보상이 필요한지"를 미리 판단하는 것은 **소비자의 결정을 발행자가 선취하는 것**이다. 발행자는 사건(성공·실패·드랍)을 알리고, **"실패가 선차감 롤백을 트리거해야 하는지"는 한도 서비스가 결정**해야 한다. 다른 서비스가 같은 결과 토픽을 구독하면서 **다른 보상 로직**을 가질 수 있다 — 예를 들어 알림 서비스는 "실패이면 사용자에게 알림", 통계 서비스는 "실패이면 메트릭 증가".

### Unknown 상태도 "실패와 같이" 처리하기

실제 구현에서 발견된 함정 하나 — **결과가 `Unknown`으로 오는 경우**가 있다. 블록체인 트랜잭션이 어떤 이유로든 "확정되지 않은 상태로 영구적으로 끝났을 때"다.

처음엔 `Unknown`을 처리하지 않아 선차감이 영원히 남는 버그가 있었다. `Unknown`도 **실패와 같이 롤백 분기**로 처리하도록 바꿨다. 사용자에게 손해가 가지 않는 쪽("한도를 되돌려 주는 쪽")으로 결정하는 게 맞다.

```go
case StatusFailed, StatusDropped, StatusUnknown:
    return c.limitService.Rollback(...)
```

이 분기를 명시적으로 두는 것은 **"미래에 새 상태가 추가되면 명시적으로 결정해야 한다"**는 알림이기도 하다. `switch`문의 `default` 분기에 `fmt.Errorf("unexpected status")`를 두면, 새 상태가 추가됐는데 처리를 안 했을 때 DLQ로 가서 알림이 울린다.

### 토큰 종류를 enum으로

같은 Saga에서 **토큰 종류별로 한도가 다르다**. 처음엔 토큰별로 테이블·컬럼을 따로 두었다가(`daily_withdrawal_tokenA`, `daily_withdrawal_tokenB`, …), 토큰이 추가될 때마다 DDL이 필요했다. **토큰 종류를 enum 컬럼**(`token_symbol`)으로 두고 한도·사용량을 그 컬럼으로 그룹핑하도록 바꿨다.

```sql
CREATE TABLE daily_withdrawal (
    wallet_address VARCHAR NOT NULL,
    token_symbol   VARCHAR NOT NULL,   -- enum처럼 쓰임
    amount         NUMERIC NOT NULL,
    used_at        TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (wallet_address, token_symbol, used_at)
);
```

새 토큰이 추가되면 **코드의 enum에 한 줄 추가**하면 끝. 테이블·컬럼은 그대로. [별도로 정리한 "결정 로직의 경계"](/lab/engineering/design/policy-as-enum/) 패턴과 같다.

## 추가로 고려할 것 — Outbox로 결과 발행 보장

결과 토픽에 메시지를 **반드시 한 번은 보내야** 보상이 트리거된다. 발행자가 "결과를 DB에 쓰고 Kafka에 보내고"를 하다가 Kafka 호출에서 실패하면 **결과가 안 보내지는 상태**가 생긴다. 이걸 피하려면 **Transactional Outbox 패턴**을 쓴다.

```sql
BEGIN;
INSERT INTO transaction_result (id, status, ...) VALUES (...);
INSERT INTO outbox (topic, payload) VALUES ('transaction.result', '{...}');
COMMIT;
-- 별도 워커가 outbox를 읽어 Kafka에 발행
```

- 얻는 것: 결과 저장과 발행이 **같은 트랜잭션**. 발행이 안 되는 상태가 영구적으로 남지 않는다.
- 치르는 것: outbox 테이블 + 워커 + 재시도 인프라.
- **보상이 반드시 필요한 금전 트랜잭션**이면 outbox가 맞다. 이 글의 케이스처럼 "한도 롤백"이 필수 보장이라면 이 패턴을 추가로 적용한다.

## 정리

| 방식 | 토픽 수 | 발행자 책임 | 소비자 로직 |
|---|---|---|---|
| 보상 전용 토픽 | 많음 | 보상 필요 여부 미리 판단 | 두 토픽 통합 상태 관리 |
| **결과 토픽 하나 (채택)** | 하나 | 결과를 그대로 발행 | 결과 상태에 따라 분기 |
| + Outbox (추가 적용) | 하나 + outbox 테이블 | 트랜잭션 보장 | 같음 |

**채택: 시도 2.** 보상은 **별도 사건이 아니라 결과의 한 분기**다. 결과 토픽 하나를 소비하면서 "실패일 때만 보상"이 가장 자연스럽고, 순서·중복·스키마를 신경 쓸 자리가 한 곳으로 모인다.

- Saga 보상을 **별도 토픽**으로 나누기 전에, 그 보상이 **결과의 한 분기로 표현 가능한지** 먼저 본다. 대부분 가능하다.
- **발행자는 사건만 알리고, 보상이 필요한지는 소비자가 결정**한다. 발행자가 미리 판단하면 다른 소비자가 다른 보상 로직을 가질 수 없다.
- 결과 상태의 `switch`는 `default` 분기를 명시해 **새 상태가 추가됐을 때 조용히 넘어가지 않게** 한다.
- `Unknown` 같은 **애매한 상태는 사용자에게 유리한 쪽**(한도 복구)으로 처리한다. 반대로 하면 사용자가 손해를 본다.
- 보상이 **반드시 한 번은 트리거되어야 하는** 금전 계산이면, 결과 발행에 **Transactional Outbox**를 추가한다.
