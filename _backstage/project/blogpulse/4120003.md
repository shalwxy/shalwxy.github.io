## ADR-001: 프론트엔드 단일 수집 경로(`POST /v1/events`)로 이벤트 파이프라인 통일

* **상태:** 승인됨 (Accepted)
* **맥락:**
  * 개인 블로그뿐 아니라 일반 웹페이지에서도 범용적으로 사용할 수 있는 이벤트 수집 파이프라인이 필요하다.
  * 초기에는 깃 블로그의 댓글·반응 위젯(`giscus`)을 위해 GitHub Webhook 수신기와 GraphQL API 조회를 백엔드에 별도로 구축하는 방안을 검토했으나, 프론트엔드 수집기(`tracker.js`)와 수집 경로가 이원화되어 이벤트 스키마가 파편화되고 외부 플랫폼 의존성이 커지는 문제가 있었다.
* **결정:**
  * 백엔드 이벤트 수집 진입점을 **`POST /v1/events` 단일 엔드포인트**로 통일한다.
  * 페이지 조회·이탈·스크롤·기기 구분뿐 아니라, 임베드 위젯(`giscus`의 `data-emit-metadata="1"` 기반 `postMessage` 카운트 증가분)이나 일반 웹페이지의 버튼 반응 이벤트까지 모두 프론트엔드(`tracker.js`)에서 표준 JSON 페이로드로 정규화해 전송한다.
* **결과 (장단점):**
  * **장점:**
    * 백엔드 수집·중복 제거·배치 적재·알림 파이프라인이 100% 단일화되어 구현 및 유지보수 복잡도가 크게 줄어든다.
    * `tracker.js` 스크립트 삽입만으로 블로그와 일반 웹사이트 어디든 동일한 구조로 확장할 수 있다.
  * **단점:**
    * 외부 임베드 위젯(`giscus`)의 Cross-Origin iframe 보안 정책상 댓글 본문 원문이나 작성자 ID는 프론트엔드에서 직접 읽을 수 없으며, 건수 변화(`delta`)만 수집할 수 있다.
    * 브라우저에서 직접 요청이 들어오므로 클라이언트 위변조를 막기 위한 Rate Limiter 및 `Idempotency-Key` 검증이 필수적이다.
* **검토한 대안과 기각 이유:**
  * *대안 1 (GitHub Webhook + 프론트 수집 병행):* 수집 어댑터와 서명 검증 로직이 중복되며, 일반 웹페이지에서는 사용되지 않을 기능에 리소스가 낭비되어 기각했다.
  * *대안 2 (프론트 수집 후 알림 시점에만 GitHub GraphQL API 조회):* 댓글 본문까지 알림에 담을 수 있으나, 외부 API 토큰 관리와 장애 포인트가 추가되고 본문 조회 요구사항이 필수적이지 않아 기각했다.
* **결정 준수 여부 검증:**
  * `Go Ingest API` 라우터에 외부 플랫폼 전용 웹훅 엔드포인트가 존재하지 않고 `POST /v1/events` 단일 경로로 모든 이벤트 타입이 유입되는지 확인한다.
  * 실제 웹페이지와 `giscus` 위젯 환경에서 `tracker.js`가 동일한 스키마로 이벤트를 발행하는지 통합 테스트로 검증한다.

## ADR-002: Data Plane(Go)과 Control Plane(Java / Spring Boot) 역할 분리

* **상태:** 승인됨 (Accepted)
* **맥락:**
  * 방문자 증가 및 페이지 이탈(`sendBeacon`) 시 발생하는 고빈도 쓰기 트래픽 처리와, 복합 조건의 대시보드 통계 조회·관리 기능은 부하 특성과 요구 역량이 다르다.
  * 단일 모놀리식으로 구현할 경우 트래픽 급증 시 대시보드 조회 응답이 지연되거나 반대로 무거운 통계 쿼리가 수집 워커의 자원을 점유할 위험이 있으며, 보유한 Go(3년)와 Java(2년) 기술 역량을 실무적 경계로 분리해 실증할 필요가 있다.
* **결정:**
  * **Data Plane (Go):** 고동시성 이벤트 수집(`202 Accepted`), Redis Streams 소비, 고루틴·채널 버퍼 기반 PostgreSQL Batch Upsert, 서킷 브레이커·지수 백오프 기반 모바일 알림 워커를 담당한다.
  * **Control Plane (Java / Spring Boot):** 일별·누적 통계 및 포스트 간 이동 흐름(`Next-Read`) 조회 API, Redis Pub/Sub 구독 기반 SSE 실시간 대시보드 스트리밍, DLQ 실패 이력 조회 및 수동 Replay 관리를 담당한다.
* **결과 (장단점):**
  * **장점:**
    * 수집·처리 계층과 조회·관리 계층의 장애 및 부하가 격리되며, 메모리 효율과 동시성 처리가 중요한 워커 영역에 Go의 강점을 집중할 수 있다.
    * Spring Boot 생태계를 활용해 복잡한 조회 쿼리, SSE 연결 관리, 관리자 기능을 빠르게 구현할 수 있다.
  * **단점:**
    * 두 언어의 런타임과 빌드 파이프라인을 함께 관리해야 하므로 단일 언어 프로젝트 대비 배포 및 스키마 동기화 비용이 발생한다.
* **검토한 대안과 기각 이유:**
  * *대안 (Go 단일 스택 또는 Java 단일 스택):* 운영 단순성은 높으나, 고빈도 스트림 워커와 복잡한 조회/관리 도메인 간의 물리적·논리적 경계 분리 설계를 보여주기 어려워 기각했다.
* **결정 준수 여부 검증:**
  * Go 서비스는 PostgreSQL에 대한 Write(Batch Upsert·알림 이력 기록)만 수행하고 복잡한 대시보드 통계 Read 쿼리를 갖지 않으며, Java 서비스는 대시보드 조회 및 DLQ Replay 재투입(`XADD`)만 담당하는지 코드 리뷰로 점검한다.

## ADR-003: 비동기 스트림 큐(Redis Streams) 및 채널 버퍼 기반 PostgreSQL Batch Upsert 도입

* **상태:** 승인됨 (Accepted)
* **맥락:**
  * 인기 글 공유 등으로 순간적인 트래픽 스파이크가 발생할 때 요청마다 PostgreSQL에 단건 `INSERT/UPDATE`를 동기 실행하면 DB 커넥션 풀 고갈과 디스크 I/O 병목이 발생해 수집 API 응답 시간이 급격히 저하된다.
  * 또한 클라이언트의 `page_leave`(`sendBeacon`) 요청은 브라우저 종료 시점에 짧은 타임아웃으로 전송되므로 수집 API의 즉각적인 수신 응답이 중요하다.
* **결정:**
  * `Go Ingest API`는 `Idempotency-Key`와 Rate Limit 검증 후 Redis Streams(`blogpulse:stream:events`)에 이벤트를 적재하고 즉시 `202 Accepted`를 반환한다.
  * `Go Stream Worker`는 Consumer Group으로 메시지를 읽어 메모리 채널 버퍼에 모은 뒤, **500건 도달 또는 200ms 경과** 조건 중 먼저 충족되는 시점에 PostgreSQL로 일괄 Batch Upsert를 수행한다.
* **결과 (장단점):**
  * **장점:**
    * 수집 API의 응답 지연이 Redis 메모리 쓰기 수준(수 ms)으로 고정되며, DB 커넥션 및 트랜잭션 오버헤드를 대폭 절감한다.
    * DB 일시 부하 시 Redis Streams가 완충 버퍼(Backpressure) 역할을 수행한다.
  * **단점:**
    * 완전 동기 방식 대비 DB 반영까지 최대 200ms의 준실시간 지연이 발생한다.
    * 워커 프로세스가 비정상 종료될 경우 메모리 버퍼에 대기 중이던 최대 500건의 이벤트가 유실되지 않도록 `Graceful Shutdown` 플러시와 Redis Streams `XACK` 시점 제어가 필요하다.
* **검토한 대안과 기각 이유:**
  * *대안 1 (수집 API에서 PostgreSQL 동기 단건 Insert):* 구현은 단순하나 동시 요청 증가 시 DB 락 경합과 레이턴시 급증이 불가피해 기각했다.
  * *대안 2 (Apache Kafka 도입):* 단일 VM 환경에서 브로커/메모리 리소스 점유가 과도하여, 이미 세션·쿨다운·재시도 큐로 사용 중인 Redis의 Streams 기능으로 통합하는 편이 효율적이라 판단해 기각했다.
* **결정 준수 여부 검증:**
  * `k6` 스파이크 부하 테스트(500 VU)를 통해 단건 동기 Insert 대비 Batch Upsert의 초당 처리량(RPS) 및 p99 지연시간 개선 수치를 측정해 검증한다.
  * `SIGTERM` 종료 시그널 수신 시 채널 버퍼 잔여 데이터를 DB에 커밋한 뒤 `XACK`를 호출하는지 통합 테스트로 확인한다.

## ADR-004: 외부 알림 장애 격리를 위한 서킷 브레이커, 지수 백오프 및 DLQ 수동 Replay 구조

* **상태:** 승인됨 (Accepted)
* **맥락:**
  * 모바일 푸시 알림 발송 대상인 외부 메신저 웹훅(Telegram, Slack, Discord, ntfy)은 네트워크 지연이나 일시적 `5xx` 장애가 발생할 수 있다.
  * 외부 알림 실패가 이벤트 수집·집계 워커 전체를 블로킹하거나, 단순 무한 재시도로 워커 스레드를 고갈시켜서는 안 되며, 최종 실패한 알림도 유실 없이 복구할 수 있어야 한다.
* **결정:**
  * 알림 발송 경로에 **서킷 브레이커**를 적용해 연속 실패 시 외부 호출을 즉시 차단(Fail-Fast)한다.
  * 일시적 실패 건은 Redis ZSET 지연 재시도 큐(`bp:retry:alerts`)에 다음 실행 시각(`+10s -> +60s -> +300s`)을 Score로 등록해 지수 백오프 재시도를 수행한다.
  * 최대 재시도(3회) 초과 시 PostgreSQL `dead_letter_events` 테이블에 실패 사유와 원본 페이로드를 저장하고, 운영자가 대시보드에서 클릭 한 번으로 스트림에 재투입(`REPLAYED`)할 수 있는 수동 Replay API를 제공한다.
* **결과 (장단점):**
  * **장점:**
    * 외부 알림 채널 장애가 핵심 트래픽 수집·DB 집계 파이프라인으로 전파되는 것을 원천 차단한다.
    * 일시적 네트워크 오류는 자동 복구되고, 장기 장애 건도 데이터 유실 없이 관측 및 재처리할 수 있다.
  * **단점:**
    * 재시도 스케줄러(ZSET 폴링 워커)와 DLQ 테이블 상태 관리(`FAILED` / `REPLAYED`), 재투입 시 중복 알림 방지 로직을 추가로 구현해야 한다.
* **검토한 대안과 기각 이유:**
  * *대안 (HTTP 클라이언트 타임아웃만 설정하고 실패 시 로그만 남김):* 장애 격리는 가능하지만 일시적 오류에도 알림이 영구 유실되고 운영자가 실패 건을 재처리할 수 없어 기각했다.
* **결정 준수 여부 검증:**
  * 알림 수신 목(Mock) 서버에 연속 500 에러 및 타임아웃을 주입해 `서킷 브레이커 Open -> ZSET 지수 백오프 재시도 -> DLQ 적재 -> 대시보드 Replay 실행 후 정상 발송`까지의 전 과정을 E2E 테스트로 검증한다.
